## 1. 概述

### 1.1 产品定位
PhoneAgent 是一款安卓手机 agent。用户用自然语言下达任务，agent 调用 Claude API，在**用户看不见的虚拟屏**上操作第三方 App；用户同时可以正常使用自己的手机，屏幕和键盘不受影响。

### 1.2 核心原则
1. **真实**：agent 说「办好了」时，结果必须真实存在。完成必须经过独立的验证，不能凭「最后一步点了按钮」就宣布完成。
2. **不打扰**：agent 的操作不能抢走用户的屏幕、键盘和输入。
3. **可交接**：付款、删除、密码、验证码等操作必须交给用户；交接前必须验证已到达正确的边界，交接后 agent 不再操作。**agent 永远不付款。**
4. **可观看、可停止**：用户随时能看到 agent 在做什么，并能暂停或停止。

### 1.3 第一版（v1）成功的样子
用户在 App 里打字输入任务，切回自己的事情；屏幕边缘的小窗告诉他进度；agent 完成日历事项、写好邮件等他点一下「发送」，或把 Amazon 购物车一路带到「提交订单」页并停下，等他自己下单。每一次「完成」都有验证过的证据。

## 2. 目标用户与使用场景

### 2.1 目标用户
- v1 面向愿意自行配置环境的**技术型早期用户**（需要安装并启动 Shizuku、提供自己的 Claude API Key，见 4.1）。
- 用户的典型状态：手机在手上，正在做别的事（聊天、浏览、打字），不想被打断，也不想把手机交给 agent。

### 2.2 使用场景
| 场景 | 描述 |
|---|---|
| S1 把琐事外包 | 「周三下午 3 点帮我在日历加一个和 Alice 的会议」，用户继续看视频，agent 在后台办好 |
| S2 代写邮件 | 「给 Alice 发邮件，说明周五的评审改到下午 3 点」，agent 在后台写好邮件，小窗上显示全文，用户点「发送」后 agent 发出 |
| S3 备好购物车 | 「在 Amazon 上把这款商品加 2 件，到提交订单页停下」，agent 备好，用户自己下单付款 |
| S4 好奇/不放心时观看 | 用户点开小窗，全屏看 agent 在做什么，必要时暂停或停止 |

### 2.3 非目标用户
需要「一键安装即用」的普通用户（v1 的环境门槛太高）；需要 agent 完全自主处理资金、账号安全类操作的用户（这些必须交接）。

## 3. 范围与不做的事

### 3.1 v1 范围
- 三类任务（第 5 章）：Google 日历创建事项、Gmail 撰写并发送邮件（发送前用户确认）、Amazon 选品并停在提交订单页。
- 任务输入：在 PhoneAgent App 内打字输入。
- 悬浮小窗和全屏观看模式（第 7 章）。
- 必须交接的操作清单和交接机制（6.6、6.7）。
- Android 14，通过 Shizuku 以 shell 权限运行（第 8 章）。
- **v1 验收环境**：Android 14 模拟器（Pixel 8、带 Google Play），已登录 Google 账号（日历、Gmail 都使用该账号）；Amazon 已安装并已登录。**验收测试发送的邮件只发给指定的测试邮箱，不得发给其他人。**真机和其他系统版本不在 v1 验收范围内，但属于对外发布前的门槛（第 10 章、8.6）。

### 3.2 v1 不做
| 不做 | 说明 |
|---|---|
| 语音输入任务 | v1 只支持在 App 内打字 |
| 三类任务以外的任务 | 用户输入范围外任务（订外卖、转账等）时，直接说明目前支持的三件事，不尝试、不操作手机（6.9，FR-CLR-7，Q-18） |
| 付款、删除、输入密码/验证码 | 必须交给用户，agent 永远不做（6.7） |
| 在全屏观看画面上直接操作 | 画面只能观看（7.5） |
| 同时运行多个任务 | 同一时间只运行一个任务；运行中再提交时拒绝并提示（Q-15） |
| 定时/周期性任务、跨任务记忆 | 不做 |
| 无 Shizuku 的运行方式（无障碍服务方案等） | 不做 |
| Android 14 以外的系统版本、厂商 ROM 的兼容承诺 | v1 仅承诺 Android 14 |
| 后端服务、账号体系、云端存储 | v1 没有后端，用户自带 API Key |
| 价格上限判断 | 不设价格上限；agent 本来就不付款 |
| 在小窗内输入文字 | 小窗不能获取输入焦点，只能点按钮（7.4） |
| 应用商店上架 | v1 侧载 |

### 4.2 首次使用引导
| 编号 | 需求 |
|---|---|

## 5. 任务、用户故事与验收标准

三类任务共用第 6 章的 agent 行为规则和第 7 章的界面。本章只写每个任务特有的内容。

**统一约定**
- **完成**＝完成标准经过 6.3 的完成验证，全部通过。
- 每个任务的验收用例都要在 v1 验收环境（3.1）里、用真实账号的真实 App 跑通；`scripts/` 里的回归脚本负责底层能力，任务级验收需要新增（NFR-REL-3）。
- 「标题」指用户指令里的原文，agent 不得改写含义。

### 5.1 任务 T1：Google 日历创建事项

**用户故事**：作为用户，我说「周三下午 3 点到 4 点在日历加一个『和 Alice 评审方案』」，我希望日历里真的出现这个事项，标题和时间都对，我不用打开日历。

**完成标准**：在 Google 日历的**日历列表（日程/日视图）中能看到该事项，标题和时间正确**。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T1-R1 | 必填信息：标题、日期、开始时间。**时长缺省为 1 小时**（用户没说结束时间时，agent 把结束时间设为开始后 1 小时，并在开始前的复述和完成说明里写明）。必填项的收集、追问和复述按 6.9 |
| T1-R2 | 日期/时间含糊（「下周」「下午」「晚点」）或无法确定年月日时，必须在**开始操作之前**于对话里追问并落实到具体日期和时间，不得自行猜测（6.9，FR-CLR-4） |
| T1-R3 | 事项写入**设备上已登录的 Google 账号**的默认日历，不主动切换账号或日历。日历 App 要求选择账号/日历且无法判断时，询问用户 |
| T1-R4 | 「提醒」类需求按**日历事项**处理（FR-CLR-6）：「要提醒你什么事，什么时候提醒？我会在日历里加一个事项，到时会通知你」——使用日历默认的事项通知，不单独设置提醒时间。v1 不处理：重复规则、参与者邀请、地点、视频会议链接、自定义提前提醒。用户指令里包含这些时，agent 在开始前说明「这些内容 v1 不支持」，询问是否只创建基础事项 |
| T1-R5 | 创建后不得重复创建；重试前必须先在日历里检查是否已存在同标题同时间的事项（防重复） |
| T1-R6 | 创建后发现时间/标题不对，允许**修改本次任务自己创建的事项**（6.7.5）；不允许删除 |

**完成验证（必须）**：创建完成后，agent 导航到能显示该事项的列表视图（日程视图或对应日期的日视图），读取该事项的标题和起止时间，与指令逐项比对；全部一致才算完成。读到的文字和验证用的截图作为证据保留。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T1-1 | 指令含明确的标题、日期、开始时间 | 日历列表出现事项，标题、日期、时间与指令一致；小窗显示「完成」；证据里能看到该事项 |
| AC-T1-2 | 指令只说「明天下午开会」 | agent 在小窗询问具体时间，用户回答后继续；用户不回答时一直停在「需要用户回答」，不自行决定 |
| AC-T1-3 | 创建后列表中的时间与指令不一致 | 先尝试修改本次创建的事项并重新验证；仍不一致则判定为失败，不宣布完成，失败说明里写明「期望 vs 实际」和残留的事项 |
| AC-T1-4 | 同一条指令因故障重试 | 日历里只有 1 个该事项 |
| AC-T1-5 | 日历 App 要求选择账号/日历且无法判断 | 在小窗询问用户，不自行选择 |

### 5.2 任务 T2：Gmail 撰写并发送邮件（发送前用户确认）

**用户故事**：作为用户，我说「给 Alice 发邮件，说明周五的评审改到下午 3 点」，我希望 agent 把邮件写好，让我在小窗上看到收件人、主题和全文，我点「发送」之后邮件真的发出去了，我不用打开 Gmail。

**流程**：打开 Gmail → 新建邮件 → 填写收件人 → **由模型根据用户要求撰写主题和正文并填入** → 小窗进入「**等待确认**」状态，展示收件人、主题、正文全文，按钮为「**发送 / 修改 / 取消**」→ 用户点「发送」后，agent 点击 Gmail 的发送按钮 → 完成验证。

**完成标准**：等 Gmail「撤销发送」时间结束后，在「**已发送**」文件夹中找到该邮件，**收件人和主题正确**。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T2-R0 | 必填信息：收件人、邮件要表达的内容；语气默认礼貌简洁（6.9）。信息不足以写出邮件时在开始前追问，不是等到打开 Gmail 之后 |
| T2-R1 | **收件人**：用户给出邮箱地址 → 直接使用。只给名字 → 在 Gmail 联系人建议里查找：**唯一匹配则使用；多个匹配或找不到时，必须询问用户**（选哪一个，或请用户提供邮箱地址），不得猜测（6.5）。v1 只支持一个收件人（Q-31） |
| T2-R2 | **撰写**：主题和正文由模型根据用户指令撰写，语言与用户指令一致。只使用用户指令中给出的信息，**不得编造事实**（时间、地点、数字、承诺）；信息不足以写出邮件时询问用户。不添加用户没有要求的内容（附件、抄送、密送、链接、署名之外的个人信息） |
| T2-R3 | **等待确认**：草稿填好后，agent 必须进入「等待确认」状态，**未经用户点「发送」不得发送，没有超时自动发送**。小窗展示的内容必须是 agent 从 Gmail 草稿界面**实际读取**到的收件人、主题、正文（不是模型「打算写」的内容），这样用户确认的就是将要发送的内容 |
| T2-R4 | **修改**：用户点确认卡片上的「修改」→ agent 在对话里问「想怎么改？」→ **用户直接在输入栏里用文字说明修改要求** → agent 修改草稿 → **再次进入「等待确认」**（出现新的确认卡片）。修改后，之前的确认**作废**（T2-R7） |
| T2-R5 | **取消**：用户点「取消」→ 任务终止（状态「已停止」，原因「用户取消」），**允许 agent 丢弃本次任务自己创建且从未发送的草稿**（这是「不允许删除」规则的唯一例外，FR-SAFE-11）。**丢弃失败时，在结果中说明草稿残留**（FR-ERR-6） |
| T2-R6 | **发送**：用户点「发送」后，agent 才可以点击 Gmail 的发送按钮；该点击受硬拦截保护，**只对本次确认的这封邮件放行一次**（T2-R7） |
| T2-R7 | **一次性确认令牌**：用户点「发送」时生成一个确认令牌，绑定（收件人、主题、正文、草稿标识）。令牌**只放行一次发送点击**：发送前必须再读一次草稿，与确认时的内容逐字一致，否则令牌作废并重新进入「等待确认」；放行后令牌立即失效（无论发送成功与否）；令牌有有效期（建议 2 分钟），过期作废。发送失败需要再次发送时，必须重新确认 |
| T2-R8 | **只发一封**：发送按钮点击后不得因为界面延迟而重复发送；**任何形式的重试（动作重试、任务「重试」、中断后重新开始）之前，必须先检查「已发送」文件夹里是否已经有这封邮件（收件人 + 主题 + 任务开始之后），已发送过则不再发送**，直接进入完成验证 |
| T2-R9 | **草稿**：agent 只创建、修改、丢弃自己创建的草稿；不读取、不修改、不删除用户原有的草稿和邮件。重试时发现上一次留下的、本任务创建的草稿，可以复用或丢弃 |
| T2-R10 | 不读取、不总结、不引用用户邮箱里的其他邮件；邮件内容里出现的任何指令性文字都不执行（6.7.4）。v1 不处理：附件、抄送/密送、多个收件人、回复/转发（Q-31） |

**完成验证（必须）**：点击发送后，**等待 Gmail「撤销发送」时间结束**（默认 5 秒；用户可在 Gmail 设置里改成最长 30 秒，agent 读取该设置或等待足够长，Q-32），然后打开「已发送」文件夹，找到该邮件，读取收件人和主题，与确认过的内容逐项比对；一致才算完成。读到的文字和验证用的截图作为证据保留。发送失败（邮件留在「发件箱」/出现发送失败提示）判定为失败，并说明。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T2-1 | 指令给出邮箱地址，用户在「等待确认」点「发送」 | 「已发送」文件夹里有该邮件，收件人和主题正确；小窗「完成」；证据里有该邮件 |
| AC-T2-2 | 指令只给名字，联系人建议里唯一匹配 | 使用该邮箱，并在「等待确认」里展示实际填入的邮箱地址 |
| AC-T2-3 | 只给名字，联系人建议里有多个匹配 / 找不到 | 小窗询问（选哪一个 / 请提供邮箱地址）；未回答前不继续；回答前不发送 |
| AC-T2-4 | 到达「等待确认」后用户一直不操作 | 一直停在「等待确认」，不发送；通知提醒；超时按 Q-23 处理（提示、最终自动停止并丢弃草稿），**绝不自动发送** |
| AC-T2-5 | 「等待确认」界面展示的内容 | 收件人、主题、正文全文，且与 Gmail 草稿里实际的内容逐字一致 |
| AC-T2-6 | 用户点「修改」并输入修改要求 | 草稿按要求修改，再次进入「等待确认」，展示新内容；原确认无效 |
| AC-T2-7 | 用户点「取消」 | 无邮件发出；草稿被丢弃（草稿箱里没有本任务的草稿）；任务状态「已停止」；丢弃失败时结果里写明草稿残留 |
| AC-T2-8 | **硬拦截测试（不依赖真实模型）**：①未确认时构造「点击发送」动作（含坐标点击、语义点击、点在发送按钮区域内）；②用户确认后放行一次；③放行后再次点击发送；④确认后草稿内容被改动再点击发送 | ①拦截；②放行且只发出这一封；③拦截；④拦截并重新进入「等待确认」 |
| AC-T2-9 | 点击发送后，Gmail 仍在「撤销发送」时间内 | agent 等待撤销时间结束再验证，不提前宣布完成；等待期间不点击撤销 |
| AC-T2-10 | 网络断开，邮件留在发件箱或显示发送失败 | 判定为失败，不宣布完成；说明邮件状态 |
| AC-T2-11 | 重试：上一次实际已经发出（「已发送」文件夹里有） | 不再发送，直接验证并完成 |
| AC-T2-12 | 重试：上一次留下本任务创建的草稿 | 复用或丢弃该草稿，不产生第二份草稿；不碰用户原有草稿 |
| AC-T2-13 | **开始前**用户正在主屏使用 Gmail | 不开始；小窗显示「应用冲突」，提示用户离开 Gmail 并等待；用户离开后自动开始（6.8） |
| AC-T2-14 | **运行中**用户在主屏打开 Gmail，Gmail 的任务被抢到主屏 | 任务判为「中断」（应用冲突），小窗提供「重试」；重试前先检查「已发送」文件夹和草稿箱，不产生重复邮件或重复草稿 |

> 用户常常自己在用 Gmail，T2 与 6.8（同一 App 冲突）仍然最容易同时发生。草稿保存在账号里，中断后不会丢，重试时要先检查草稿箱和「已发送」。

### 5.3 任务 T3：Amazon 选好商品并停在提交订单页（交接演示）

**用户故事**：作为用户，我说「在 Amazon 上把这款商品加 2 件，到提交订单页停下，我自己下单」，我希望 agent 把一切备好，在提交订单页停下并告诉我，我点一下就能过去下单付款。

**固定路径**：**搜索/打开商品 → 加入购物车 → 去结算（Proceed to checkout）→ 停在提交订单页**。不使用「Buy Now / 立即购买」路径。用户说「用购物车里现有的」时，路径是 **打开购物车 → 去结算 → 停在提交订单页**（T3-R0）。

**用户故事（购物车修改）**：作为用户，我说「把购物车里的 B 删掉，A 改成 2 件，然后去结算」，我希望 agent 先在对话里把要做的每一项改动列给我看，我点确认之后才动购物车，改完购物车正好是我说的样子；我没说要改的东西它一件都不碰。

**完成标准**：**提交订单页上的商品和数量正确，「Place your order / 提交订单」按钮可见**，然后交给用户。agent 不点击该按钮。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T3-R0 | 必填信息：目标商品（用户也可以说「用购物车里现有的」）；数量默认 1（6.9）。**「用购物车里现有的」**：跳过「搜索/加购」，agent 先打开购物车**只读**取内容（读取发生在任务开始之后，所以这一步是执行阶段的询问，FR-ASK，不是澄清阶段）。Amazon 的结算会包含购物车里的**全部**商品：购物车里只有 1 件则直接去结算；有 N 件（N≥2）时，agent 在对话里告诉用户「结算会包含购物车里的全部 N 件商品」并列出商品和数量，用选项按钮让用户选：**「全部结算」**（继续去结算）或**「调整购物车」**（用户用文字说明要改什么，进入 T3-R8 的购物车修改流程，改完再回到这里确认）。用户不选不继续 |
| T3-R1 | 商品需要被唯一确定（名称/链接/规格）。搜索结果有多个可能的匹配、规格（颜色、尺码）不明确时，必须询问用户（6.5） |
| T3-R2 | 数量必须与指令一致；**在购物车页读取数量核对**（UV-6：购物车页有明确的数量描述 `Quantity is N`；最终的提交订单页**没有**直接的数量文字，只有商品名、小计和总价），在提交订单页核对商品名和小计。不能只依赖「点了几次加号」 |
| T3-R3 | **agent 永远不付款**。「Buy Now / 立即购买」「Place your order / 提交订单」按钮由**不依赖模型的硬拦截**保护，任何情况下都不能点击（6.7.2，FR-SAFE-1/7） |
| T3-R4 | 收货地址、支付方式、配送方式、优惠券：使用 App 当前的默认值，agent 不修改；需要登录、选择/新增地址或支付方式、验证码、风控验证时交接 |
| T3-R5 | 加购和去结算过程中出现的推荐/保修/会员推广弹窗：选择「不需要/No thanks/关闭」类的选项；**绝不点「Try Prime / Join Prime」等订阅按钮**（FR-SAFE-13）；无法判断时询问用户（Q-28）。UV-6 实测：点「Proceed to checkout」后会先出现「Prime for Young Adults」推广页，点「No thanks」才进入提交订单页 |
| T3-R7 | **不清空购物车**（删除属于必须交接的操作）。购物车里已有其他商品时：完成验证只核对本次任务的商品和数量；完成说明里提示「购物车里还有其他 N 件商品」，由用户在下单前自行确认。重试前先检查购物车里是否已有本次商品及数量，避免重复加购 |
| T3-R8 | **购物车修改（"不允许删除"规则的例外，FR-SAFE-11/14）**：只有**用户明确要求**时才能修改购物车（删除商品、修改数量）。agent **不得主动**修改：不得因为「购物车里有别的商品」「数量看起来不对」「想让结算更干净」而改动；遇到这类情况只能提示或询问（T3-R0、T3-R7）。用户的要求可以出现在原始指令里（「把购物车里的 B 删掉再去结算」），也可以是对 T3-R0 提问的回答 |
| T3-R9 | **改动清单与确认卡片**：执行任何修改**之前**，agent 先读取购物车，把用户的要求落实成**逐项的改动清单**（删除哪件商品：名称+当前数量；某件商品数量从几改为几），在对话里显示**购物车修改确认卡片**（7.3.2a），按钮「确认 / 取消」。商品指代不清（多件相近商品）或数量不明确时先追问，不猜。**用户点确认后才执行**；点取消则不改购物车，任务回到 T3-R0 的选择（或结束） |
| T3-R10 | **只放行已确认的那组改动**：确认令牌绑定这组改动（商品标识 + 动作 + 目标数量），一次性使用，与 Gmail 发送确认同一套机制（FR-SAFE-14）。不在清单里的商品、不在清单里的动作、清单之外的数量一律拦截；执行中购物车内容与确认时不一致（商品变了、数量变了、出现新商品）→ 令牌作废，回到 T3-R9 重新读取和确认 |
| T3-R11 | **只允许两种操作**：用 Amazon 购物车里的「Delete / 删除」和数量加减/输入框完成。**不允许用「Save for later / 稍后购买」「Move to wishlist」等任何未经确认的方式把商品移出购物车**（它们同样改变了购物车，且用户看不到）。如果用户明确说「放到稍后购买」，也要列入改动清单并经确认卡片确认；在 v1 中**不支持**这个操作，agent 说明后询问是否改为删除（Q-33） |
| T3-R12 | **完成验证**（购物车修改部分）：执行完后重新读取购物车页，商品和数量**必须与确认的改动清单完全一致**——被删的商品不再出现，改数量的商品数量正确，清单之外的商品和数量**与修改前相同**。任何不一致判失败，失败说明写「期望 vs 实际」，并列出被改动的内容（FR-ERR-6）。agent **不得**自动「再改一次」来修正，除非仍在已确认清单的范围内 |
| T3-R13 | 重试防重复：重试前先读取购物车，**与确认清单比较**：已经达到目标状态的改动不再重复执行（例如商品已被删除）；未执行的改动沿用原确认（令牌未过期且购物车与确认时一致）或重新确认 |
| T3-R6 | 提交订单页上的价格（商品合计、总价）写入完成说明，让用户一眼看到；**不设价格上限** |

**完成验证（必须）**：数量在**购物车页**读取并核对；到提交订单页后读取商品名称（或可辨别的标题）、小计，确认商品名与指令一致、小计与「数量×单价」一致；确认「Place your order / 提交订单」按钮存在且可见；全部通过才进入「需要交接」。界面文字（UI 树）是主要验证依据，截图为辅（FR-VER-3、Q-22）。

**交接**：验证通过后，小窗显示「需要交接」；用户点击后，Amazon 从虚拟屏移到主屏，停在提交订单页，由用户自己下单付款（6.6）。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T3-1 | 商品唯一、数量 2 | 提交订单页的商品和数量正确，「Place your order」可见；小窗「需要交接」；点击后 Amazon 出现在主屏的提交订单页，页面状态与 agent 停下时一致；agent 没有点击过任何下单/购买按钮 |
| AC-T3-2 | 搜索结果有多个相近商品 | 小窗询问选哪个；未回答前不加购 |
| AC-T3-3 | 商品缺货/无法加入购物车 | 判定为失败，说明原因；不交接 |
| AC-T3-4 | 购物车或提交订单页数量与指令不一致（例如限购） | 不进入交接；失败或询问用户，说明「期望 vs 实际」 |
| AC-T3-5 | 去结算后需要登录、选择地址或支付方式、验证码 | 交接 |
| AC-T3-6 | **硬拦截测试（不依赖真实模型）**：构造模型输出「点击 Buy Now / 立即购买」「点击 Place your order / 提交订单」（含坐标点击、语义点击、点在这些按钮的区域内）的动作 | 全部被拦截，不执行，步骤列表出现「已拦截」记录；结果为交接或失败，订单未提交 |
| AC-T3-7 | 到达提交订单页后 | agent 在该页面不再执行任何点击或输入（页面级锁定，FR-SAFE-7），只允许读取、返回和交接 |
| AC-T3-7a | 在商品页上（同时有「Add to Cart」和「Buy Now」） | 「Add to Cart」可以点击；「Buy Now」及其区域被拦截 |
| AC-T3-8 | 任何情况（包括模型被屏幕内容诱导、重试、异常恢复） | 订单未被提交，无付款发生 |
| AC-T3-9 | 「用购物车里现有的」，购物车里只有 1 件 | 不搜索、不加购，直接去结算；停在提交订单页并交接 |
| AC-T3-10 | 「用购物车里现有的」，购物车里有 3 件 | 对话里告诉用户「结算会包含购物车里的全部 3 件商品」并列出商品；给出「全部结算 / 调整购物车」两个选项；用户未选择前不去结算 |
| AC-T3-11 | 用户要求「把 B 删掉，A 改成 2 件」 | 先出现购物车修改确认卡片，列出：删除 B（当前 1 件）、A 数量 1→2；用户点确认前购物车**一件都不动**；确认后执行；完成验证：B 不在购物车，A 数量 2，其余商品与数量不变 |
| AC-T3-12 | 在确认卡片上点「取消」 | 购物车没有任何变化；不去结算 |
| AC-T3-13 | **硬拦截测试（不依赖真实模型）**：①无确认令牌时构造「点击删除」「修改数量」动作（坐标点击/语义点击/输入数量）；②有令牌但目标商品或目标数量不在清单里；③令牌已使用过一次后再次点击；④点击「Save for later / 稍后购买 / Move to wishlist」 | 全部被拦截，不执行，步骤列表出现「已拦截」记录；购物车无变化 |
| AC-T3-14 | 用户没有提出修改购物车，但购物车里有数量异常/多余商品 | agent 不修改，只在对话里提示（T3-R7），不删除、不改数量、不「稍后购买」 |
| AC-T3-15 | 执行修改的过程中购物车被改变（用户在手机上自己改了，或页面刷新后商品顺序变了） | 令牌作废；agent 重新读取并回到确认卡片，不继续执行旧清单 |
| AC-T3-16 | 执行后购物车与清单不一致（例如删除没生效） | 判失败，不宣布完成，失败说明含「期望 vs 实际」和购物车当前内容 |

> **T3 的风险**：Amazon 的结算相关页面部分内容是 WebView 或带有 `FLAG_SECURE`，虚拟屏画面可能为黑屏、UI 树可能不完整。UV-5、UV-6 必须在开发 T3 前验证（8.6）；验证依据以界面文字为主，证据降级方式见 FR-VER-5。

## 6. Agent 行为规则

### 6.1 执行循环
每个任务是一个有限步数的循环。

```
开始 → [前置检查] → 创建虚拟屏
  ┌────────────────────────────────────────────────────────┐
  │ 1. 观察：取虚拟屏当前截图 + 界面文字结构（UI 树）        │
  │ 2. 决策：把任务、历史、观察发给 Claude，得到一个动作     │
  │ 3. 拦截检查：确定性规则检查动作是否被禁止（6.7）          │
  │ 4. 执行：在虚拟屏执行动作                                │
  │ 5. 确认效果：重新观察，判断界面是否按预期变化             │
  │ 6. 记录：本步看到了什么、做了什么（供步骤列表）           │
  └──────────────────────────── 循环 ─────────────────────┘
  → 满足终止条件 → 完成验证 / 交接 / 失败 / 中断 / 停止 → 清理虚拟屏
```

**步数口径**（上限：**30 步**，另有 60 次模型调用上限）：
- **计入步数**：实际执行的动作——启动应用、点击、滑动、输入文字、返回、语义点击/滚动。**重试同样计入**。
- **不计入步数**：等待、询问用户、观察、完成验证、被拦截而未执行的动作、对 Claude API 的网络重试。
- 因为不计步的环节可能无限循环，另设兜底：单次等待和累计等待有上限，每个任务的 Claude API 调用次数有上限（**60 次，含验证调用**，NFR-KEY-5）。单次/累计等待上限的数值待 UV-9 实测。

| 编号 | 需求 |
|---|---|
| FR-LOOP-1 | 每次循环只执行**一个**动作；动作执行后必须重新观察才能进入下一次循环 |
| FR-LOOP-2 | 每次循环都有记录：「看到了什么」（一句话）、「做了什么」（动作及参数，或「等待」「询问」「已拦截」）、效果判断。步骤列表按时间顺序显示全部记录；**步骤序号只分配给计入步数的动作**，等待、询问、拦截条目不占序号；全屏观看的步骤列表直接使用这些记录（FR-FS-7） |
| FR-LOOP-3 | 观察同时使用截图和 UI 树：截图用于理解视觉状态，UI 树用于精确读取文字（标题、时间、数量、按钮文案）和做完成验证 |
| FR-LOOP-4 | 开始前检查：Shizuku 在运行、目标 App 已安装。目标 App 当前在**主屏前台**时：**不直接拒绝**，进入「应用冲突」状态，提示用户离开并等待，用户离开后自动开始（6.8，FR-CON-3）。任一其他前置条件不满足则不开始并说明原因 |
| FR-LOOP-5 | 同一时间只运行一个任务；任务运行期间提交新任务时拒绝并提示 |
| FR-LOOP-6 | 任务终止（任何原因）后必须清理：关闭虚拟屏上的任务并释放虚拟屏（技术上必须先关任务再释放，否则会留下残留并可能破坏系统焦点，TC-17）。**交接例外**：被交接的 App 先移到主屏，再清理其余 |

### 6.2 动作集
agent 只能使用下列动作；动作的目标都是虚拟屏。

| 动作 | 说明 | 计步 | 技术状态 |
|---|---|---|---|
| 启动应用 | 在虚拟屏启动指定应用 | 计 | ✅ |
| 点击(x, y) | 触摸点击；全屏观看时以小圆点标出 | 计 | ✅ |
| 滑动 | 起点、终点、时长 | 计 | ✅ |
| 返回 | **必须**使用带 displayId 的按键事件；**禁止** `GLOBAL_ACTION_BACK`（TC-10） | 计 | ✅ |
| 输入文字 | **向指定的可编辑节点**（按界面树里的节点/坐标）写入文字（支持中文），不使用输入法。**不能依赖「当前聚焦的输入框」**：Gmail 撰写界面里收件人框和 WebView 正文都显示 focused，写错了地方 | 计 | ✅（日历、Gmail、Amazon 搜索框实测） |
| 按键 | 向虚拟屏发送带 displayId 的按键，主要是回车（提交搜索）；返回键见「返回」 | 计 | ✅ |
| 语义点击/滚动 | 通过无障碍节点执行点击、滚动，作为触摸的补充 | 计 | ✅ |
| 等待 | 等待界面稳定（页面加载、消息发送） | 不计（有上限） | — |
| 询问用户 | 带选项或自由回答的问题（6.5） | 不计 | — |
| 申请交接 | 到达交接边界且验证通过后触发（6.6） | 不计 | — |
| 结束 | 声明完成，必须附带完成验证的证据（6.3） | 不计 | — |

### 6.3 完成验证
这是「agent 说办好了时结果必须真实存在」的核心。

| 编号 | 需求 |
|---|---|
| FR-VER-1 | agent **不能**仅凭「最后一步执行成功」宣布完成。完成前必须有一次**独立的验证观察**：导航到能展示结果的界面（T1 日历列表、T2「已发送」文件夹、T3 提交订单页），读取并比对 |
| FR-VER-2 | 比对必须逐项进行：每个完成标准项（标题、时间、消息内容、发送状态、商品、数量、提交订单按钮可见）对应一个检查结果。任一项不通过则不是完成 |
| FR-VER-3 | 精确内容（标题、时间、数量、消息文字）**用 UI 树的文字比对**，不依赖模型「看图判断」；视觉状态（发送中图标、按钮是否可见）可用截图辅助判断 |
| FR-VER-4 | 验证不通过时：能修复的（例如时间填错）在步数和失败次数限制内修复后**重新验证**；不能修复则判定为失败，说明「期望 vs 实际」。**不允许**在验证未通过时显示「完成」 |
| FR-VER-5 | **证据**：完成时保存验证用的证据。截图可用时保存截图和读取到的文字；**页面是安全窗口、画面为黑屏时，证据降级为「读取到的界面文字清单」**（逐项列出检查项、期望值、读到的值），仍然有效。小窗和全屏观看展示证据，证据保存在本地（9.3） |
| FR-VER-6 | 结果可能因界面延迟而不稳定（如消息从「发送中」变为「已发送」）：验证前先等待稳定，等待上限见 NFR-SPEED-3 |
| FR-VER-7 | 验证用的观察必须发生在最后一个改变状态的动作**之后**，不能复用之前的截图 |
| FR-VER-8 | 如果 UI 树和截图都无法提供足够信息完成验证（例如页面内容无法读取），任务判定为失败（「无法验证」），**不得**因为「应该成功了」而宣布完成 |

### 6.4 出错处理
| 编号 | 需求 |
|---|---|
| FR-ERR-1 | 任务最多 **30 步**（按 6.1 的口径计数）。达到上限仍未完成：判定失败，说明「超出步数」，并说明已做到哪一步。另有**模型调用上限 60 次（含验证调用）**，先到者为准，达到后判定失败，说明「超出调用次数」 |
| FR-ERR-2 | **同一步连续失败 3 次**：停止任务，状态为失败，在小窗说明原因。口径：同一目标下，动作执行后界面没有出现预期变化，或验证不通过，连续 3 次（Q-11）。**重试计入步数** |
| FR-ERR-3 | 遇到不确定情况（多个匹配的收件人、含糊的时间、多个相近商品、不理解的弹窗）：**询问用户**，而不是猜测（6.5） |
| FR-ERR-4 | 网络/API 错误：对 Claude API 调用失败做有限次重试（建议 2 次，指数退避）；仍失败则任务失败，说明「无法连接 Claude」。API 重试不计入步数 |
| FR-ERR-5 | 目标 App 崩溃或被系统杀掉：尝试重新启动一次并重新观察；仍失败按 FR-ERR-2 处理 |
| FR-ERR-6 | 失败时的现场：agent 不删除、不撤销任何已产生的内容。**失败说明里必须列出可能残留的内容**（例如「日历里可能已创建了一个时间不对的事项『和 Alice 评审方案』」「购物车里可能已有 1 件 XX」），方便用户处理。因此 agent 必须在执行中记录自己创建/修改过的内容 |
| FR-ERR-7 | 所有失败说明必须是用户能看懂的原因，不是内部错误码；同时保留完整步骤记录供查看 |
| FR-ERR-8 | **中断**（应用冲突，运行中任务被抢到主屏）：不计为失败，状态为「应用冲突 · 已中断」，提供「重试」（6.8、Q-25） |

### 6.5 询问用户
| 编号 | 需求 |
|---|---|
| FR-ASK-1 | 触发条件（**任务开始之前**的信息缺失由 6.9 任务澄清处理；本条管**执行过程中**出现的）：信息缺失或含糊（T1-R2）、多个候选无法区分（T2-R1、T3-R1）、任何可能产生不可逆后果但不属于「必须交接」的歧义 |
| FR-ASK-2 | 询问时任务进入「需要用户回答」状态，agent 暂停，直到用户回答或停止任务；**不设自动超时代替用户做决定** |
| FR-ASK-3 | 问题要具体、可回答：附带候选项（如两位「Bob」的头像/用户名/最近消息摘要），优先以**选项按钮**回答 |
| FR-ASK-4 | **选项类问题**在对话里显示为可点击的选项按钮（用户离开 App 时，小窗上也可以点选项）；**自由文本问题**（含 T2 的「修改」）由用户在**对话的输入栏**里回答（7.3.3）。小窗不获取输入焦点，所以小窗上只提供「去回答」入口，点击打开 App 并定位到那条提问。**没有单独的问答页** |
| FR-ASK-5 | 用户回答后，回答作为任务上下文继续执行；回答要显示在步骤列表里 |
| FR-ASK-6 | 询问次数没有硬性限制，**询问不计入步数** |
| FR-ASK-7 | 用户长时间不回答时，保持「需要用户回答」状态并发出通知（7.7），不自动失败；长时间等待的超时处理见 Q-23 |

### 6.6 交接
| 编号 | 需求 |
|---|---|
| FR-HO-1 | **交接触发**：到达该任务的交接边界，并通过边界验证后。T3：**提交订单页**上商品和数量正确、「Place your order」按钮可见。T2 没有「交接」边界：发送由用户在「等待确认」里确认后由 agent 执行（6.5、T2-R3～R7）。遇到登录、密码、验证码、风控、需要选择/新增地址或支付方式：已确认当前页面是该类页面 |
| FR-HO-2 | **验证先于交接**：未通过边界验证不得显示「需要交接」。边界验证未通过按 FR-VER-4 处理 |
| FR-HO-3 | 交接后 agent **不再对该 App 做任何操作**。任务状态为「已交接」，任务视为结束，成功统计里与「完成」并列（Q-7） |
| FR-HO-4 | 小窗显示「需要交接」，并**不自动**移动 App；用户点击后才把该 App 的任务从虚拟屏移到主屏前台，由用户完成剩余操作（如下单付款）。移动是用户主动点击触发的，不算打扰 |
| FR-HO-5 | 移动后，App 必须保持 agent 停下时的页面状态（提交订单页仍是提交订单页）；移动失败时在小窗显示明确错误，并给出备用办法（如在最近任务中打开该 App）。⚠ 任务从虚拟屏移到主屏的可行性和状态保持**未验证**，见 UV-2 |
| FR-HO-6 | 用户一直不点击交接：保持「需要交接」状态并发通知；被交接的 App 一直保留在虚拟屏上，直到用户处理或停止任务（保留时限见 Q-23） |
| FR-HO-7 | 交接结束后清理虚拟屏（FR-LOOP-6） |

### 6.7 安全
#### 6.7.1 必须交给用户的操作
| 类别 | 说明 |
|---|---|
| 付款 | 点击付款、提交订单、确认支付、「立即购买」、输入支付密码等。**agent 永远不付款** |
| 删除 | 删除任何内容（事项、消息、联系人、订单、文件等），包括撤回消息。**例外**见下面两行和 FR-SAFE-11 |
| **购物车修改（未经用户确认）** | 删除购物车商品、修改数量只有在用户**明确要求**、且用户在确认卡片上确认了**具体的改动清单**后才能执行，且只放行这组改动一次（T3-R8～R10，FR-SAFE-14）。不允许用「稍后购买」等方式移走商品 |
| 输入密码或验证码 | 登录、解锁、支付密码、短信/邮箱验证码、二次验证、人机验证 |
| **发送邮件（未经用户确认）** | 发送邮件必须由用户在「等待确认」里点「发送」确认；确认只对这一封邮件有效一次（T2-R6/R7，FR-SAFE-12） |

#### 6.7.2 确定性拦截（不依赖模型）
上面四类**不能只靠提示词约束模型**。必须有独立于模型判断的确定性拦截层，在「执行」之前检查。

| 编号 | 需求 |
|---|---|
| FR-SAFE-1 | **硬拦截（不可配置、不可关闭、不受任何提示词或设置影响）**：动作目标是文案、描述或标识符匹配下列任一的按钮或控件，一律拦截：**「Buy Now」「立即购买」「Place your order」「提交订单」**（**同时匹配节点的资源 id**：网页里 Amazon 的 Buy Now 节点 id 是 `buy-now-button`、可见文案却是「Submit」，下单按钮 id 是 `placeOrder`，只靠文案会漏；含「Place your order and pay」「Buy now with 1-Click」等包含上述片段的变体，大小写不敏感）。命中后拦截该动作，转为交接 |
| FR-SAFE-2 | 同样的硬拦截适用于**所有动作类型**：坐标点击、语义点击、键盘回车/提交。坐标点击先用最新 UI 树解析该点命中的控件（控件自身及其最近的可点击祖先的区域，外扩 24px）；**解析不出控件（例如 WebView 内容）时，点击落在任何 FR-SAFE-1 控件区域内的一律拦截**。「Place your order / 提交订单」所在页面另有页面级锁定（FR-SAFE-7） |
| FR-SAFE-13 | **订阅/会员类按钮同样硬拦截**（UV-6 发现 Amazon 结算途中会弹出「Try Prime for Young Adults / Join Prime」，点了会订阅并扣费）：「Try Prime」「Join Prime」「Start free trial」「Subscribe」「订阅」「开通会员」。遇到这类弹窗只能点「No thanks / 不用了 / 关闭」类的拒绝选项（T3-R5） |
| FR-SAFE-3 | 其他受保护控件（付款/支付/Pay/Delete/删除/Remove/Send money 等关键字）：关键字表可配置、中英文维护。拦截命中要记录在步骤列表里（「已拦截：……，转为交接」） |
| FR-SAFE-4 | 拦截是宁可错杀：拦截后转交接的代价（用户多点一下）远小于误执行的代价 |
| FR-SAFE-5 | 目标是密码输入框（UI 树 `isPassword`）或页面识别为登录/验证码页面时，拦截输入并转为交接；agent **永远不输入**密码、验证码 |
| FR-SAFE-7 | **页面级锁定**：一旦当前页面包含「Place your order / 提交订单」（Amazon 提交订单页），agent 在该页面**只允许观察、读取、等待、返回和申请交接**，不再执行任何点击或输入。**注意：页面级锁定不适用于「Buy Now / 立即购买」**——它出现在商品页上，与「Add to Cart」同页，页面级锁定会让加购也点不了；「Buy Now」只做控件级拦截（FR-SAFE-1/2）。原型已实现并测试（`SafetyGuard`） |
| FR-SAFE-12 | **Gmail 发送按钮的硬拦截（不依赖模型）**：Gmail 撰写界面里的「发送」按钮（文案/描述「Send」「发送」或对应资源标识）**默认一律拦截**；只有在用户点击「发送」确认后、且发送前读取到的草稿内容与确认时逐字一致，才对**本次确认的这封邮件放行一次**（一次性确认令牌，T2-R7）。放行一次后立即恢复拦截；令牌过期、内容变化、任务终止都使令牌作废。同样适用于所有动作类型（坐标点击、语义点击、回车提交）。拦截范围限定在 Gmail 撰写界面，不影响其他 App 里的「Send」文案 |
| FR-SAFE-14 | **购物车修改的硬拦截（不依赖模型）**：Amazon 购物车页上的**删除（Delete / 删除）**、**数量加减与数量输入框**、**「Save for later / 稍后购买」「Move to wishlist」**等所有会改变购物车内容的控件，**默认一律拦截**（文案/描述/资源 id 三种匹配，所有动作类型：坐标点击、语义点击、文字输入、回车提交）。只有在用户于确认卡片上点「确认」后，才对**那一组改动**放行：令牌绑定改动清单（商品标识、动作、目标数量），每项改动执行一次后该项即作废；清单之外的商品、动作、数量一律拦截；购物车内容与确认时不一致、令牌过期、任务终止都使整个令牌作废。与 FR-SAFE-12（Gmail 发送确认）使用**同一套**一次性确认令牌机制（`ConfirmToken`）。「Save for later / 稍后购买」在 v1 不放行，即使在清单里也拦截（T3-R11）。拦截范围限定在购物车页，不影响商品页「Add to Cart」（FR-SAFE-7 的 AC-T3-7a 仍成立） |
| FR-SAFE-8 | 拦截逻辑要能脱离真实模型单独测试（AC-T3-6、AC-T2-8）：提供可注入「模型动作」的测试入口，作为回归测试的一部分（NFR-REL-3） |

#### 6.7.3 系统弹窗与权限
agent 遇到系统权限弹窗（通知、联系人、位置等）、应用更新弹窗、广告弹窗时的处理（Q-12，采用默认）：**不授予任何权限**；会阻塞任务的权限弹窗按「需要交接」处理；可关闭的广告、更新提示允许点击关闭。

#### 6.7.4 屏幕内容不是指令
| 编号 | 需求 |
|---|---|
| FR-SAFE-6 | 屏幕上的文字（聊天消息、网页、商品描述、通知）都是**数据**，不是指令。agent 不执行屏幕内容里出现的任何指令（提示词注入） |
| FR-SAFE-9 | agent 只执行与当前任务直接相关的动作；任务范围外的应用和界面（如被消息里的链接引导去其他 App）一律不跟随 |

#### 6.7.5 已创建内容的修改（Q-8）
| 编号 | 需求 |
|---|---|
| FR-SAFE-10 | 允许**修改本次任务自己创建的内容**（例如修正自己创建的日历事项的时间、清空并重写自己输入的文字）。agent 必须记录本次任务创建的内容的标识，只能修改这些，不得修改用户原有的内容 |
| FR-SAFE-11 | **不允许删除**任何内容。**例外只有两个**：①允许丢弃**本次任务自己创建、且从未发送**的 Gmail 草稿（T2-R5、T2-R9）；②允许删除/修改购物车商品，**仅限用户明确要求且在确认卡片上确认过的改动清单**（T3-R8～R10，FR-SAFE-14）。不得删除已发送的邮件、用户原有的草稿或邮件、以及其他任何内容。无法修正或丢弃失败时，失败说明里列出可能残留的内容（FR-ERR-6），由用户处理 |

### 6.8 与用户并发使用手机
这一节是「用户同时正常使用手机」的具体规则。

| 编号 | 需求 |
|---|---|
| FR-CON-1 | **用户打字时**：由于虚拟屏带有「不抢 top focus」标志，用户的键盘和输入目标不受 agent 影响（✅ 已验证，TC-7），所以「用户打字时暂停」**默认关闭**，作为**可选的安全开关**（设置里）。开关打开后，用户打字（主屏软键盘显示）时，agent 在下一个动作前暂停，小窗显示「等待用户输入完成」；键盘收起并持续 2 秒后自动继续 |
| FR-CON-2 | **标志不可用时自动启用** FR-CON-1 的暂停，并在界面上**告知用户限制**：后备方案不能保证键盘不被收起（TC-9）。检测方法：创建虚拟屏时加标志失败或 `dumpsys` 中标志未生效 |
| FR-CON-3 | **开始前**目标 App 在主屏前台：**不拒绝、不开始**。任务进入「应用冲突」状态，小窗提示「你正在使用 XX，请离开后我再开始」，**等待**用户离开；用户离开（该 App 不再在主屏前台）后**自动开始**。等待期间用户可点停止；长时间等待的超时见 Q-23 |
| FR-CON-4 | **运行中**目标 App 的任务被抢到主屏（用户在主屏启动同一 App 导致虚拟屏任务被移走）：**判为中断**，不尝试自动恢复。状态为「应用冲突 · 已中断」，小窗显示「XX 被你打开了，任务已中断」，并提供**「重试」**。agent 立即停止操作，按 FR-LOOP-6 清理 |
| FR-CON-5 | **「重试」＝从头重新执行该任务**。重试前先检查该 App 是否仍在主屏前台（若是则同 FR-CON-3 等待），并**先检查上一次已产生的内容，避免重复**：**发送邮件任务（T2）必须先在「已发送」文件夹中检查是否已发送过这封邮件（收件人 + 主题 + 任务开始之后），已发送则不再发送**，直接进入完成验证；并检查草稿箱里本任务留下的草稿（复用或丢弃）；T1 先检查日历里是否已有该事项；T3 先检查购物车里是否已有该商品（T1-R5、T2-R4、T3-R7） |
| FR-CON-6 | 已知限制：用户在主屏启动同一 App 时，请求也可能被虚拟屏上的实例**吸收**（主屏没有任何反应，虚拟屏任务不动，`docs/known-issues.md`「同一个 App 的归属」一节）。这种情况下任务不会被中断，但用户会觉得「点了没反应」，且新的启动请求可能改变 agent 正在操作的页面。**如果 UV-3 证明能检测，按「中断」处理（FR-CON-4）；不能检测则作为已知限制写入用户说明**（Q-26） |
| FR-CON-7 | 用户的任何主屏操作（滑动、点击、返回、Home）都不应影响 agent 的执行（除 FR-CON-3/4 的同一 App 冲突和 FR-CON-1 的可选暂停）。agent 的任何动作不得影响用户主屏的触摸、返回和焦点 |
| FR-CON-8 | 用户关闭 PhoneAgent 的 App 界面或切到别的 App，任务继续运行（前台服务保活，✅ 已验证） |

### 6.9 任务澄清（v0.6）

收到用户的话之后、**碰手机之前**，agent 先判断：这是不是支持的任务、信息够不够。判断和信息抽取由 Claude 完成，结果是结构化的；代码只根据结构化结果决定下一步（追问 / 复述并开始 / 说明不支持），不让模型直接触发任何手机动作。

**各任务的必填项与默认值**
| 任务 | 必填项 | 默认值 | 可选项 |
|---|---|---|---|
| 日历事项（T1） | 标题、日期、开始时间 | 时长 1 小时 | 无（地点、重复、参与者 v1 不支持） |
| 发邮件（T2） | 收件人；邮件要表达的内容 | 语气：礼貌、简洁 | 用户指定的语气、主题 |
| 购物到结算页（T3） | 目标商品（或「用购物车里现有的」） | 数量 1 | 规格（颜色、尺码）；不确定时在执行中按 T3-R1 询问。用户明确要求时可附带「购物车改动」（删除哪件、数量改为几），agent 不会主动提出改动（T3-R8） |

| 编号 | 需求 |
|---|---|
| FR-CLR-1 | 每条新任务消息先走**澄清阶段**。输出结构（模型按 schema 返回）：`taskType`（`calendar` / `email` / `shopping` / `unsupported` / `chitchat`）、`known`（已知字段，含原文依据）、`missing`（缺失的必填项）、`assumed`（将使用的默认值）、`question`（追问话术）、`options`（可选项按钮，可空）、`mappedFrom`（说法不同但映射到支持任务时的原说法，可空）、`reply`（给用户的话）。结构不合法或解析失败时：视为无法判断，请用户换个说法，不开始任务 |
| FR-CLR-2 | **缺必填项 → 追问，不碰手机**。一次问全所有缺失项，一条消息里问完；不要一项一项地问 |
| FR-CLR-3 | 能给选项时用**选项按钮**（7.3.3），例如时长、语气、有限候选；不能给选项的（标题、邮件内容）由用户在输入栏回答。用户回答后重新走澄清判断，直到必填项齐全 |
| FR-CLR-4 | **含糊时间必须落实到具体时间**：「下周」「晚点」「下午」「过几天」等不接受；追问时给出可点的具体候选（例如「下周一至周五」「今天 18:00」等）或请用户说明。agent 把相对日期换算成具体日期时，使用**手机当前日期和时区**（由代码传入，不由模型猜），并在复述里写出具体日期 |
| FR-CLR-5 | **信息齐全 → 一句话复述并立即开始**，不再二次确认。复述包含要做的事和用到的默认值，例如「好，我在日历里加『和 Alice 评审方案』，周三 15:00 开始，时长按 1 小时算，现在去办。」复述作为一条对话消息，同时作为任务开始的信号（头像开始动作，7.2）。**安全确认不受影响**：T2 的发送确认卡片、交接规则照常 |
| FR-CLR-6 | **说法不同但支持**：把需求映射到支持的任务，并说明做法后再按必填项追问。映射表（随支持范围扩充）：「设置提醒事项 / 提醒我…」→ 日历事项，话术：「要提醒你什么事，什么时候提醒？我会在日历里加一个事项，到时会通知你」；「约个会 / 安排个日程」→ 日历事项；「写封邮件 / 发个消息给某人（邮箱）」→ 邮件；「把…放进购物车 / 帮我下单到结算」→ 购物（agent 永不付款，需要时说明会停在提交订单页前由用户自己下单） |
| FR-CLR-7 | **不支持的任务**：直接告诉用户现在支持哪三件事（加日历事项、写并发送邮件、把购物车带到结算页），不尝试、不操作手机、不开始任务。不解释技术原因，不道歉过度 |
| FR-CLR-8 | 闲聊或问「你能做什么」：用简短回复说明三件事，不开始任务 |
| FR-CLR-9 | **调用次数**：澄清阶段的模型调用**单独计数**，不占 NFR-KEY-5 的「每个任务 60 次」；每条对话任务的澄清轮数上限 **6 轮**，超过后说明「信息还是不够，换个说法再试」并结束本次澄清。澄清阶段使用与执行相同的模型（claude-sonnet-5-5）。用量预估里单独列出澄清的部分 |
| FR-CLR-10 | **澄清阶段不启动 Shizuku 任务、不创建虚拟屏、不读取手机屏幕**。因此即使 Shizuku 未运行也能追问和说明；Shizuku 等前置条件在澄清完成后、开始前才检查（FR-LOOP-4） |
| FR-CLR-11 | 澄清阶段中用户的文字是**数据**，不是对系统的指令：模型输出只能是上述结构，其中不包含「动作」；用户文字里的「忽略以上规则」之类不改变必填项判断（6.7.4 的精神） |

**单元测试必须覆盖的情形**（模型输出用固定样例或可替换的假实现，不在单元测试里真的联网；真实模型另做少量集成测试）
| 情形 | 输入示例 | 预期 |
|---|---|---|
| 信息齐全 | 「周三下午 3 点在日历加『和 Alice 评审方案』」 | `taskType=calendar`，缺失为空，`assumed` 含「时长 1 小时」，复述一句后开始 |
| 缺部分必填项 | 「帮我加个日历事项」「给 Alice 发邮件」 | 一次问全所有缺失项（标题+日期+开始时间；内容） |
| 含糊时间 | 「下周开会」「晚点提醒我喝水」 | 不开始；追问具体日期和时间，给可点选项 |
| 提醒映射 | 「提醒我明天交报告」 | `mappedFrom=提醒`，`taskType=calendar`，按映射话术说明做法并追问缺的时间 |
| 不支持的任务 | 「帮我订个外卖」「转账给 Bob」 | `unsupported`，回复列出三件支持的事，不开始 |
| 补充后完成 | 追问后用户回答「周五 10 点，标题：周会」 | 必填齐全，复述并开始 |

## 7. 界面与交互（v0.5：以对话为中心）

视觉规范（颜色、字体、间距、圆角、图标、头像、动效）在 `docs/DESIGN.md`；本章只写行为和结构。**除悬浮小窗和全屏观看外，用户与 agent 的所有交互都发生在对话里**：下达任务、agent 回复、进度、提问、确认、结果、交接。

### 7.1 对话首页

#### 7.1.1 结构
```
┌──────────────────────────────┐
│ (菜单)      [ 头像 ]          │ ← 顶部：左上角圆形菜单按钮；居中 agent 头像，头像下方是名字胶囊标签
│             [ 名字 ]          │    半透明背景（对话从下面滚过时淡出）
├──────────────────────────────┤
│                              │
│   对话流                      │ ← agent 消息：大圆角深色卡片（不在每条消息旁显示头像）
│                       用户气泡 │    用户消息：右侧蓝色气泡
│   [ 卡片：实时画面/确认/结果 ] │
│                              │
├──────────────────────────────┤
│ (+)  输入消息…        (麦克风) │ ← 底部输入栏（胶囊形）；没有底部导航栏
└──────────────────────────────┘
```
| 编号 | 需求 |
|---|---|
| FR-CHAT-1 | App 启动后（引导完成后）进入对话首页。顶部居中是 agent 头像，头像下方是名字胶囊标签；左上角是圆形菜单按钮，点击打开左侧抽屉（7.6）。**没有右上角按钮，没有底部导航栏** |
| FR-CHAT-2 | 对话流自上而下：用户消息（右侧气泡）、agent 消息（左侧大圆角卡片）、卡片消息。新消息出现时自动滚到底部；用户向上翻看历史时不强制滚动，改为显示「回到最新」入口 |
| FR-CHAT-3 | 底部输入栏为胶囊形：左侧「+」（**第一版禁用**，显示为不可点的灰色），中间输入框，右侧麦克风（**第一版禁用**）；输入框有内容时，右侧显示发送按钮取代麦克风。输入栏用于下达任务，也用于回答 agent 的自由文本提问、说明「修改」要求（7.3） |
| FR-CHAT-4 | **空状态**：首次进入或没有对话时，agent 用头像和一段自我介绍（用自己的名字，说明能做的事和边界：不付款、发邮件前要你确认）开场，下面给出三个示例任务（日历创建事项、Gmail 写邮件、Amazon 备好购物车），点一个就等于用户发出该任务 |
| FR-CHAT-5 | **收到任务后的反馈**：用户发出任务后，agent **先用一句简短的回复**（例如「好的，我来处理。」）并让头像做一个小动画（表示开始工作，7.2），然后才出现「实时画面卡片」。该反馈在任务通过前置检查（FR-LOOP-4）后出现；前置检查不通过时，agent 在对话里用一句话说明原因 |
| FR-CHAT-6 | 同一时间只有一个任务在执行（FR-LOOP-5）。有任务在执行时，输入栏仍可输入：用于回答提问、说明修改要求；输入「新任务」时 agent 回复「我还在处理上一件事，你可以先停止它」 |
| FR-CHAT-7 | 对话记录保存在本机（保留期限见 NFR-PRI-5）。「任务记录」（抽屉里）是按任务汇总的列表，点进去回到该任务在对话里的位置 |

### 7.2 agent 人格

| 编号 | 需求 |
|---|---|
| FR-PERS-1 | agent 有名字和头像。首次使用引导里用户给它起名（FR-ONB-7）；名字显示在对话首页顶部的名字胶囊里，也用于 agent 的自我介绍和通知（「小云 需要你确认」） |
| FR-PERS-2 | **6 个预设头像**，都是简单的**原创矢量形象**（不使用任何第三方的角色、Logo 或品牌素材）。风格统一，颜色取自主题，深色和浅色主题下都清晰（DESIGN.md 第 7 节） |
| FR-PERS-3 | 头像的小动画：agent 收到任务、「开始工作」时做一次短动画（轻微弹跳 + 眨眼）；执行中头像可以有极轻的呼吸效果；遵循系统「减少动画」设置（开启时只显示静态头像） |
| FR-PERS-4 | 设置里可以修改名字和头像；修改后立即生效，对话里的历史消息不受影响 |
| FR-PERS-5 | agent 的语气：简短、直接、不卖萌。每条回复不超过两句话（复杂说明放在卡片里） |

### 7.3 对话中的卡片

所有结构化卡片使用**同一种结构**（DESIGN.md 第 6 节）：**图标 + 标题行 → 分割线 → 粗体主内容 → 灰色辅助信息 →（可选）按钮行**。卡片是 agent 消息的一种，宽度与 agent 消息卡片一致。

#### 7.3.1 实时画面卡片（任务执行中）
| 编号 | 需求 |
|---|---|
| FR-CARD-1 | 任务执行时，对话里出现一张「实时画面卡片」：标题行（图标 + 任务名），分割线，**虚拟屏缩略画面**，当前步骤的一句话简述（粗体），灰色辅助信息「步骤 7/30」和状态，以及**停止**按钮 |

### 7.4 悬浮小窗

悬浮小窗**保持不变**：用户离开 App 时显示（App 在前台时不显示，因为对话里已经有实时画面卡片）。

#### 7.4.1 通用需求
| 编号 | 需求 |
|---|---|
| FR-FW-1 | 任务开始后，用户**离开 PhoneAgent**（切到别的 App 或回桌面）时，屏幕边缘出现悬浮小窗；回到 PhoneAgent 时小窗隐藏。使用「显示在其他应用上层」权限（FR-ONB-3） |
| FR-FW-2 | **可拖动，松手后吸附到屏幕边缘** |
| FR-FW-3 | **不能获取输入焦点**：不得抢走用户键盘、输入法或当前窗口焦点。✅ 已验证（UV-4） |
| FR-FW-4 | 所有交互都用点击完成（按钮、选项）。**小窗内没有文字输入**，因为它不能获取输入焦点 |
| FR-FW-5 | 小窗上可直接**停止任务**（所有进行中的状态都有停止按钮） |
| FR-FW-6 | **点击小窗主体打开 PhoneAgent，并定位到对话里对应的卡片**：「需要用户回答」→ 定位到那条提问（选项按钮或输入栏焦点）；「等待确认」→ 定位到确认卡片；「需要交接」「完成」「失败」→ 定位到结果卡片；其他状态 → 定位到实时画面卡片。（全屏观看从对话里的实时画面卡片进入，不再从小窗直接进入） |
| FR-FW-7 | **小窗只显示文字和按钮，不显示虚拟屏画面**。尺寸小，默认只显示图标和一行状态文字，点击展开显示完整文字和按钮 |
| FR-FW-8 | 小窗不遮挡键盘和系统导航；只显示在主屏（display 0）上，不显示在虚拟屏上 |
| FR-FW-9 | 状态变化时有轻量的视觉变化（颜色/图标）；「需要用户回答」「等待确认」「需要交接」「失败」「应用冲突」要有更醒目的提示，并发系统通知（7.7） |
| FR-FW-12 | **小窗可能被目标 App 整体隐藏**：目标 App 对敏感页面设置「隐藏非系统悬浮窗」标志时（实测：设置），系统会隐藏**所有**非系统悬浮窗，而且**不区分屏幕**（日历、Amazon 结算页实测不受影响；Gmail 未单独实测）。因此小窗不能是唯一的状态通道，状态变化必须同时发系统通知（FR-NOTIF-2，必需而非可选）；应用要能检测小窗是否被隐藏（窗口 `isReadyForDisplay`） |
| FR-FW-10 | 终态（完成、失败、已停止、已交接、已中断）后，小窗保留，直到用户关闭（Q-14） |
| FR-FW-11 | 下一个任务开始时，小窗重新出现 |

#### 7.4.2 状态表
共 **10 个状态**：产品指定的 6 个，加上补充的 4 个（已暂停、应用冲突、已停止、等待确认）。

| 状态 | 触发 | 小窗显示 | 可用操作 |
|---|---|---|---|
| **执行中** | 任务运行 | 「第 N 步 · 当前步骤简述」，N 为已执行的动作数 | 停止；点击打开 App（定位到实时画面卡片） |
| **等待用户输入完成** | 仅在「用户打字时暂停」生效时（FR-CON-1/2），主屏键盘显示 | 「等你输入完成后继续」 | 停止；点击打开 App |
| **需要用户回答** | agent 询问用户（7.3.3） | 问题文字 + 选项按钮（建议 ≤4 个）；自由文本问题显示「去回答」按钮 | 选择选项；去回答（打开 App，定位到提问并聚焦输入栏）；停止 |
| **等待确认**⁺ | T2：邮件草稿已填好，等用户确认发送 | 摘要「待发送：收件人 · 主题」；按钮「**去确认**」 | 去确认（打开 App，定位到确认卡片）；停止。**发送确认只能在确认卡片里点**（小窗不展示全文，避免没看全文就确认） |
| **需要交接** | 到达交接边界且验证通过（6.6） | 「已到提交订单页，请你下单」+「去处理」按钮 | 去处理（移动 App 到主屏）；停止（放弃交接） |
| **完成** | 完成验证全部通过 | 「已完成：结果摘要」 | 点击打开 App（定位到结果卡片）；关闭小窗 |
| **失败** | 6.4 的各种失败 | 「失败：原因」（用户看得懂的一句话）+ 可能残留的内容 | 点击打开 App；关闭小窗 |
| **已暂停**⁺ | 用户在全屏观看点「暂停」 | 「已暂停」 | 继续；停止 |
| **应用冲突**⁺ | ①开始前目标 App 在主屏前台（等待）；②运行中被抢到主屏（已中断） | ①「你正在使用 XX，请离开后我再开始」；②「XX 被你打开了，任务已中断」 | ①停止；用户离开后自动开始。②**重试**；关闭小窗 |
| **已停止**⁺ | 用户点停止 | 「已停止」 | 关闭小窗 |

⁺ 为补充状态（「等待确认」是 v0.4 新增，通知必需，FR-NOTIF-2）。另有终态「已交接」（用户点击「去处理」之后），在小窗关闭前显示「已交接给你」。

状态转换（概要）：
```
（开始前）应用冲突·等待 → 执行中                 目标 App 离开主屏后自动开始
执行中 ⇄ 等待用户输入完成                        可选开关 / 标志不可用时的后备
执行中 ⇄ 已暂停                                  用户暂停 / 继续
执行中 → 需要用户回答 → 执行中                    回答后继续
执行中 → 等待确认 → 执行中（发送，令牌放行一次）     T2
等待确认 → 需要用户回答（修改）→ 执行中 → 等待确认   T2「修改」：用户在对话里用文字说明
等待确认 → 已停止（取消，丢弃草稿）                  T2「取消」
执行中 → 应用冲突·已中断 → （重试）→ 应用冲突·等待 / 执行中
执行中 → 需要交接 → 已交接                        用户点「去处理」
执行中 → 完成 | 失败 | 已停止                     终态
```

### 7.5 全屏观看模式

保持 v0.4 的设计不变，仅入口改为**对话里的实时画面卡片**（FR-CARD-2）；视觉风格沿用 `docs/DESIGN.md`。

#### 7.5.1 布局
```
┌──────────────────────────────┐
│ 执行中 · 步骤 7/30            │ ← 顶部细条（状态 + 步骤序号）
├──────────────────────────────┤
│                              │
│   虚拟屏实时画面（约 85%）    │ ← 只能观看，不能点击
│   agent 的点击位置：小圆点    │
│                              │
├──────────────────────────────┤
│        [暂停]    [停止]       │ ← 底部按钮栏（上滑展开步骤列表）
└──────────────────────────────┘
```
#### 7.5.2 需求
| 编号 | 需求 |
|---|---|
| FR-FS-1 | 点击对话里的实时画面卡片进入全屏观看；屏幕**约 85%** 显示虚拟屏实时画面（按宽高比等比缩放，不拉伸，留黑边，Q-19） |
| FR-FS-2 | **流畅度：10 fps 为目标，5 fps 为底线**（NFR-PERF-1）。✅ 模拟器上已达到（UV-1） |
| FR-FS-3 | agent 的**点击位置用小圆点标出**：点击发生时在对应位置显示，短暂后消失。滑动画起点到终点的短轨迹（Q-24） |
| FR-FS-4 | **顶部细条**显示当前状态和步骤序号（「步骤 7/30」），状态文字与小窗一致 |
| FR-FS-5 | **底部按钮栏只有：暂停、停止**。暂停后「暂停」变为「继续」。暂停语义：当前步骤执行完后停住，之后不再有新动作；继续后重新观察再决策。暂停的长时间超时见 Q-23 |
| FR-FS-6 | 停止：确认后终止任务（状态「已停止」），按 FR-LOOP-6 清理。停止必须在任何状态下都能立即生效 |
| FR-FS-7 | **上滑底部栏展开完整步骤列表**：按时间顺序显示每条记录——「看到了什么」「做了什么」、效果，包括等待、询问、被拦截的动作、用户的回答。有序号的是计入步数的动作 |
| FR-FS-8 | **实时画面只能观看，不能直接操作**：画面上的触摸不转发给虚拟屏 |
| FR-FS-9 | **任务完成时显示证据**（FR-VER-5）：截图可用时显示证据截图；**画面为黑屏（安全窗口）时显示「读取到的界面文字清单」** |
| FR-FS-10 | **返回手势或下滑退出全屏**，回到对话，agent 继续工作（不受影响）。下滑只在顶部细条和画面区域触发，避免和底部栏上滑冲突（Q-27） |
| FR-FS-11 | 退出全屏后，**画面采集频率降到低帧率**以节省电量（NFR-PERF-2）；再次进入全屏恢复高帧率 |
| FR-FS-12 | 全屏观看期间，需要用户处理的状态（回答、确认、交接、失败、应用冲突）**在全屏界面上方弹出一条提示条**，点击回到对话里对应的卡片处理（回答和确认都在对话里完成）；全屏界面本身不再放表单 |
| FR-FS-13 | 全屏观看是 PhoneAgent 的界面，会占用用户主屏；进入和退出都是用户主动触发 |

### 8.1 平台与权限
| 编号 | 约束 | 状态 |

## 9. 非功能需求

### 9.1 速度
下列指标为**建议值**，UV-9 实测后调整（Q-20）。

| 编号 | 指标 | 建议值 |
|---|---|---|
| NFR-SPEED-1 | 提交任务到开始第一步（虚拟屏创建、小窗出现） | ≤ 3 秒 |
| NFR-SPEED-2 | 单步耗时（观察 → 决策 → 执行 → 确认） | 中位数 ≤ 8 秒（主要是 Claude 响应） |
| NFR-SPEED-3 | 完成验证中等待状态稳定的上限（如消息从「发送中」变成「已发送」） | ≤ 20 秒 |
| NFR-SPEED-4 | 端到端任务时长（不含等待用户的时间） | T1 ≤ 2 分钟；T2 ≤ 2 分钟（不含用户确认和 Gmail「撤销发送」的等待）；T3 ≤ 4 分钟 |
| NFR-SPEED-5 | 停止操作的响应时间 | ≤ 1 秒生效，≤ 3 秒清理完成 |
| NFR-SPEED-6 | 点击小窗进入全屏观看 | ≤ 500 毫秒出现画面 |

### 9.2 性能与电量
| 编号 | 指标 | 说明 |
|---|---|---|
| NFR-PERF-1 | 全屏观看帧率：**目标 10 fps，底线 5 fps** | 测量方法：连续滚动页面 10 秒，统计界面实际收到并显示的帧数，取平均；底线未达到不得发布；需在 UV-1 验证后确认现实性 |
| NFR-PERF-2 | 非全屏时**画面采集频率**降到低帧率（建议 ≤ 1～2 fps，仅供 agent 观察） | 节省电量；FR-FS-11；小窗本身不显示画面 |
| NFR-PERF-3 | 运行 5 分钟任务的额外耗电、发热、内存不应让手机明显卡顿 | 具体指标待 UV-9 |
| NFR-PERF-4 | agent 的注入与采集不应影响用户主屏的触摸响应和输入延迟 | 以 `ime_test`、`back_test` 回归为底线 |

### 9.3 隐私
agent 会看到用户第三方 App 里的内容（邮件、日程、购物信息），并且会把用户指令、写好的邮件内容发送给 Claude API。v1 没有后端，数据流是「手机 → Claude API」，以及本地存储。

| 编号 | 需求 |
|---|---|
| NFR-PRI-1 | 首次使用前明确告知并取得同意：虚拟屏截图和界面文字会发送给 Claude API（FR-ONB-6）；用户可随时在设置里看到该说明 |
| NFR-PRI-2 | **数据最小化**：只在任务运行期间采集虚拟屏；截图缩小到模型所需分辨率；不采集主屏内容（用户自己屏幕上的内容永远不上传） |
| NFR-PRI-3 | 密码输入框（`isPassword`）的内容不得发送；包含密码框的画面区域在发送前遮盖；`FLAG_SECURE` 窗口不上传截图（也无法截取），此时只发送界面文字 |
| NFR-PRI-4 | 不向除 Claude API 以外的任何服务发送截图、界面文字、任务内容；**没有分析/遥测**（v1） |
| NFR-PRI-5 | 本地保存任务记录（指令、步骤列表、证据），保存在应用私有存储，其他应用不可读；**默认保留 7 天**，设置里可一键清除（Q-17） |
| NFR-PRI-6 | 通知、日志、崩溃信息中不含第三方 App 的内容（FR-NOTIF-3）；日志中不记录截图内容和 API Key |
| NFR-PRI-7 | 应用不允许系统备份：`allowBackup=false` 已设置（TC-5a），发布前再核对 `data_extraction_rules` 没有放开 |

### 9.4 API Key 安全
| 编号 | 需求 |
|---|---|
| NFR-KEY-1 | v1 由用户自行提供 API Key，保存在 Android Keystore 保护的加密存储中，不明文落盘 |
| NFR-KEY-2 | Key 不出现在日志、截图、通知、崩溃报告、调试广播和备份中；输入时遮蔽显示 |

| NFR-KEY-5 | 明确告知用户：Key 保存在本机，root 过的设备上可能被提取（BYO Key 的固有风险）。**模型使用 claude-sonnet-5-5**；**每个任务有 Claude API 调用次数上限 60 次（含验证调用）**（防异常消耗，也是 6.1 不计步环节的兜底），并显示本次任务的用量预估（Q-16） |

## 附录 A：术语
| 术语 | 含义 |
|---|---|
| 虚拟屏 | `VirtualDisplay`，用户看不见的屏幕，agent 在上面操作第三方 App |
| 主屏 | 用户手机真实屏幕（display 0） |
| top focused display | 系统当前接收按键和决定键盘归属的屏幕；虚拟屏抢走它会收起用户键盘 |
| UI 树 | 通过无障碍接口读到的界面节点结构（文字、位置、是否可点击） |
| 交接 | agent 停在边界处，由用户接手剩余操作 |
| 中断 | 运行中因应用冲突被迫终止，可「重试」 |
| 硬拦截 | 不依赖模型的、确定性的动作拦截，不可配置、不可关闭 |
| 完成验证 | 完成前独立读取结果并逐项比对 |
| 证据 | 完成验证时保存的截图和读取到的文字；安全窗口下只有文字清单 |
