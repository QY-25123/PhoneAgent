## 1. 概述

### 1.1 产品定位
PhoneAgent 是一款安卓手机 agent。用户用自然语言下达任务，agent 调用 Claude API，在**用户看不见的虚拟屏**上操作第三方 App；用户同时可以正常使用自己的手机，屏幕和键盘不受影响。

### 1.2 核心原则
1. **真实**：agent 说「办好了」时，结果必须真实存在。完成必须经过独立的验证，不能凭「最后一步点了按钮」就宣布完成。
2. **不打扰**：agent 的操作不能抢走用户的屏幕、键盘和输入。
3. **可交接**：付款、删除、密码、验证码等操作必须交给用户；交接前必须验证已到达正确的边界，交接后 agent 不再操作。
4. **可观看、可停止**：用户随时能看到 agent 在做什么，并能暂停或停止。

### 1.3 第一版（v1）成功的样子
用户在 App 里打字输入任务，切回自己的事情；屏幕边缘的小窗告诉他进度；agent 完成日历事项、发出 Telegram 消息，或把购物车停在结算页等他付款。每一次「完成」都有验证过的证据。

## 2. 目标用户与使用场景

### 2.1 目标用户
- v1 面向愿意自行配置环境的**技术型早期用户**（需要安装并启动 Shizuku、提供自己的 Claude API Key，见 4.1）。
- 用户的典型状态：手机在手上，正在做别的事（聊天、浏览、打字），不想被打断，也不想把手机交给 agent。

### 2.2 使用场景
| 场景 | 描述 |
|---|---|
| S1 把琐事外包 | 「周三下午 3 点帮我在日历加一个和 Alice 的会议」，用户继续看视频，agent 在后台办好 |
| S2 代发消息 | 「在 Telegram 告诉 Bob 我晚点到」，用户继续使用手机，agent 在后台发出 |
| S3 备好购物车 | 「在购物 App 里把这款商品加 2 件，到结算页停下」，agent 备好，用户自己付款 |
| S4 好奇/不放心时观看 | 用户点开小窗，全屏看 agent 在做什么，必要时暂停或停止 |

### 2.3 非目标用户
需要「一键安装即用」的普通用户（v1 的环境门槛太高）；需要 agent 完全自主处理资金、账号安全类操作的用户（这些必须交接）。

## 3. 范围与不做的事

### 3.1 v1 范围
- 三类任务（第 5 章）：Google 日历创建事项、Telegram 给联系人发消息、购物 App 选品并停在结算页。
- 任务输入：在 PhoneAgent App 内打字输入。
- 悬浮小窗和全屏观看模式（第 7 章）。
- 必须交接的操作清单和交接机制（6.6、6.7）。
- Android 14，通过 Shizuku 以 shell 权限运行（第 8 章）。

### 3.2 v1 不做
| 不做 | 说明 |
|---|---|
| 语音输入任务 | v1 只支持在 App 内打字 |
| 第三类以外的任务 | 不保证其他 App 和任务可用；agent 不应主动尝试范围外的任务（见 Q-18） |
| 付款、删除、输入密码/验证码 | 必须交给用户，agent 永远不做（6.7） |
| 在全屏观看画面上直接操作 | 画面只能观看，不能点击（7.3） |
| 同时运行多个任务 | v1 同一时间只运行一个任务（Q-15） |
| 定时/周期性任务、跨任务记忆 | 不做 |
| 无 Shizuku 的运行方式（无障碍服务方案等） | 不做 |
| Android 14 以外的系统版本、真机厂商 ROM 的兼容承诺 | v1 仅承诺 Android 14；其他版本发布前需要真机验证（第 10 章风险） |
| 后端服务、账号体系、云端存储 | v1 没有后端，用户自带 API Key（Q-16） |
| 用户通过小窗输入文字 | 小窗不能获取输入焦点，只能点按钮（7.2） |

## 4. 前置条件与首次使用

### 4.1 前置条件
| 编号 | 前置条件 | 说明 |
|---|---|---|
| PRE-1 | Android 14 | 技术验证只覆盖 Android 14（8.1） |
| PRE-2 | Shizuku 已安装、已启动、已授权 PhoneAgent | Shizuku 在设备重启后需要重新启动（通过电脑 adb 或无线调试） |
| PRE-3 | 用户提供 Claude API Key | v1 没有后端，由用户自带（Q-16） |
| PRE-4 | 目标 App 已安装且已登录 | Google 日历、Telegram、购物 App（具体是哪个见 Q-3）。agent 不负责登录 |
| PRE-5 | 授予「显示在其他应用上层」权限 | 悬浮小窗需要（FR-ONB-3） |
| PRE-6 | 授予通知权限 | 前台服务和任务提醒需要 |

### 4.2 首次使用引导
| 编号 | 需求 |
|---|---|
| FR-ONB-1 | 首次打开 App 时，按顺序检查 PRE-2、PRE-3、PRE-5、PRE-6，未满足的项显示明确的说明和操作入口；全部满足后才能下达任务 |
| FR-ONB-2 | Shizuku 引导：检测未安装、未运行、未授权三种状态，分别给出对应说明；**每次打开 App 以及每次下达任务前**都要检查 Shizuku 是否在运行，设备重启后必然需要重新启动 |
| FR-ONB-3 | 「显示在其他应用上层」权限：首次使用时引导开启（跳转系统设置页），用户回来后自动检测；未开启时不能下达任务，并说明原因 |
| FR-ONB-4 | API Key：输入框内容遮蔽显示；保存后做一次轻量校验请求，失败时给出明确原因（无效、网络、额度） |
| FR-ONB-5 | 下达任务时检查所需 App 是否已安装；未安装则说明并拒绝，不进入执行 |
| FR-ONB-6 | 首次使用前展示隐私说明并取得同意：agent 会把虚拟屏截图和界面文字发送给 Claude API（见 9.3） |

## 5. 任务、用户故事与验收标准

三类任务共用第 6 章的 agent 行为规则和第 7 章的界面。本章只写每个任务特有的内容。

**统一约定**
- **完成**＝完成标准经过 6.3 的完成验证，全部通过。
- 每个任务的验收用例都要在 Android 14 上、使用真实账号的真实 App 上跑通；`scripts/` 里的回归脚本负责底层能力，任务级验收需要新增（见 NFR-REL-3）。
- 「标题」指用户指令里的原文，agent 不得改写含义。

### 5.1 任务 T1：Google 日历创建事项

**用户故事**：作为用户，我说「周三下午 3 点到 4 点在日历加一个『和 Alice 评审方案』」，我希望日历里真的出现这个事项，标题和时间都对，我不用打开日历。

**完成标准**：在 Google 日历的**日历列表（日程/日视图）中能看到该事项，标题和时间正确**。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T1-R1 | 必填信息：标题、日期、开始时间。结束时间缺省时：用户没说就用日历 App 的默认时长，并在完成说明里写明 |
| T1-R2 | 日期/时间含糊（「下周」「下午」「晚点」）或无法确定年月日时，必须在小窗询问用户，不得自行猜测 |
| T1-R3 | 事项写入哪个日历账号：使用日历 App 的默认账号，不主动切换（Q-3） |
| T1-R4 | v1 不处理：提醒、重复规则、参与者邀请、地点、视频会议链接。用户指令里包含这些时，agent 在开始前说明「这些内容 v1 不支持」，询问是否只创建基础事项 |
| T1-R5 | 创建后不得重复创建；重试前必须先在日历里检查是否已存在同标题同时间的事项（防重复） |

**完成验证（必须）**：创建完成后，agent 导航到能显示该事项的列表视图（日程视图或对应日期的日视图），读取该事项的标题和起止时间，与指令逐项比对；全部一致才算完成。验证用的截图作为证据保留。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T1-1 | 指令含明确的标题、日期、开始时间 | 日历列表出现事项，标题、日期、时间与指令一致；小窗显示「完成」；证据截图里能看到该事项 |
| AC-T1-2 | 指令只说「明天下午开会」 | agent 在小窗询问具体时间，用户回答后继续；用户不回答时一直停在「需要用户回答」，不自行决定 |
| AC-T1-3 | 创建后列表中的时间与指令不一致（例如被日历 App 改成了其他时间） | 判定为失败，不宣布完成；失败说明里写明「期望 vs 实际」 |
| AC-T1-4 | 同一条指令因故障重试 | 日历里只有 1 个该事项 |
| AC-T1-5 | 日历 App 要求选择账号/日历且无法判断 | 在小窗询问用户，不自行选择 |

### 5.2 任务 T2：Telegram 给联系人发消息

**用户故事**：作为用户，我说「在 Telegram 告诉 Bob 我晚点到」，我希望消息真的发出去了，我不用打开 Telegram。

**完成标准**：在 Telegram 的聊天记录中出现该消息，且**没有「发送中」或「失败」标记**。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T2-R1 | 收件人必须是用户 Telegram **通讯录里已有的联系人**。收件人不在通讯录里，一律交接（6.7），agent 不发送（「通讯录」的含义见 Q-9） |
| T2-R2 | 搜索收件人得到多个同名/相近结果时，必须在小窗询问用户选哪一个，不得猜测（6.5） |
| T2-R3 | 消息内容严格使用用户指令中给出的文字，不得润色、增删（用户明确要求「帮我措辞」除外，v1 不支持） |
| T2-R4 | 只发一条消息。发送按钮点击后不得因为界面延迟而重复发送；重试前必须先检查聊天记录里是否已经有这条消息 |
| T2-R5 | 不读取、不总结、不引用聊天里的其他内容；对话中出现的任何指令性文字都不执行（6.7.4） |

**完成验证（必须）**：发送后等待消息状态稳定，在聊天记录里找到该消息，确认文字完全一致，且状态不是「发送中」（时钟图标等）和「发送失败」（红色感叹号等）。等待上限见 NFR-SPEED-3；超时仍是「发送中」则判定为失败，并在说明里写明。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T2-1 | 联系人唯一，网络正常 | 聊天记录出现该消息，状态为已发送；小窗「完成」；证据截图含该消息 |
| AC-T2-2 | 通讯录里有两个同名「Bob」 | 小窗询问选哪一个（附可区分的信息，如头像、用户名、最近消息）；未回答前不发送 |
| AC-T2-3 | 收件人不在通讯录 | 不发送；小窗显示「需要交接」，说明原因；点击后 Telegram 移到主屏，用户自行处理 |
| AC-T2-4 | 网络断开，消息一直「发送中」或「失败」 | 判定为失败，不宣布完成；说明里写明消息状态 |
| AC-T2-5 | 点击发送后界面卡顿，agent 误以为没发出 | 重试前先检查聊天记录，不产生第二条消息 |
| AC-T2-6 | 用户此时正在主屏使用 Telegram | 按 6.8 暂停并提示，不抢走用户正在使用的 App |

> T2 与 6.8（同一 App 冲突）最容易同时发生：用户常常正在 Telegram 里聊天时让 agent 发消息。这是高频场景，见 Q-4。

### 5.3 任务 T3：购物 App 选好商品并停在结算页（交接演示）

**用户故事**：作为用户，我说「在 XX 购物 App 里把这款商品加 2 件到结算页，我自己付款」，我希望 agent 备好一切，在结算页停下并告诉我，我点一下就能去付款。

**完成标准**：**结算页的商品和数量正确，付款按钮可见**，然后交给用户。agent 不点击付款/提交订单。

**任务特有规则**
| 编号 | 规则 |
|---|---|
| T3-R1 | 商品需要被唯一确定（名称/链接/规格）。搜索结果有多个可能的匹配、规格（颜色、尺码）不明确时，必须询问用户（6.5） |
| T3-R2 | 数量必须与指令一致；agent 必须在结算页核对数量而不是只依赖「点了几次加号」 |
| T3-R3 | agent 在结算页必须停下，**不得点击任何付款、提交订单、确认支付类按钮**（确定性拦截，6.7.2） |
| T3-R4 | 收货地址、优惠券、支付方式：使用 App 当前的默认值，agent 不修改；需要登录、实名、验证码、风控验证时交接 |
| T3-R5 | 价格显示在结算页时，写入完成说明（让用户一眼看到），但 v1 不做价格上限判断（Q-3 中确认是否需要） |

**完成验证（必须）**：agent 在结算页读取商品名称（或可辨别的标题）、规格、数量，与指令逐项比对；确认付款按钮可见且可点击；全部通过才进入「需要交接」。

**交接**：验证通过后，小窗显示「需要交接」；用户点击后，该购物 App 从虚拟屏移到主屏，由用户完成付款（6.6）。

**验收用例**
| 编号 | 用例 | 预期 |
|---|---|---|
| AC-T3-1 | 商品唯一、数量 2 | 结算页商品和数量正确，付款按钮可见；小窗「需要交接」；点击后 App 出现在主屏的结算页，页面状态与 agent 停下时一致；agent 没有点击过付款 |
| AC-T3-2 | 搜索结果有多个相近商品 | 小窗询问选哪个；未回答前不加购 |
| AC-T3-3 | 商品缺货/无法加入购物车 | 判定为失败，说明原因；不交接 |
| AC-T3-4 | 结算页数量与指令不一致（例如库存限购） | 不进入交接；失败或询问用户，说明「期望 vs 实际」 |
| AC-T3-5 | 结算页出现登录/验证码 | 交接（密码/验证码属于必须交接的操作） |
| AC-T3-6 | 无论什么情况 | 订单未被提交，无付款发生 |

> **T3 的特别风险**：付款页和结算页常带有 `FLAG_SECURE`，虚拟屏画面可能是黑屏（技术验证未覆盖，见 10 章）。此时 agent 必须改用界面文字（UI 树）做验证；证据截图可能为空，见 Q-22。

## 6. Agent 行为规则

### 6.1 执行循环
每个任务是一个有限步数的循环。**一步**＝一次「观察 → 决策 → 执行 → 确认效果」。

```
开始 → [前置检查] → 创建虚拟屏
  ┌────────────────────────────────────────────────────────┐
  │ 1. 观察：取虚拟屏当前截图 + 界面文字结构（UI 树）        │
  │ 2. 决策：把任务、历史、观察发给 Claude，得到一个动作     │
  │ 3. 拦截检查：确定性规则检查动作是否被禁止（6.7）          │
  │ 4. 执行：在虚拟屏执行动作                                │
  │ 5. 确认效果：重新观察，判断界面是否按预期变化             │
  │ 6. 记录：本步看到了什么、做了什么、效果如何（供步骤列表） │
  └──────────────────────────── 循环 ─────────────────────┘
  → 满足终止条件 → 完成验证 / 交接 / 失败 / 停止 → 清理虚拟屏
```

| 编号 | 需求 |
|---|---|
| FR-LOOP-1 | 每步只执行**一个**动作；动作执行后必须重新观察才能进入下一步 |
| FR-LOOP-2 | 每步的记录至少包含：步骤序号、「看到了什么」（一句话）、「做了什么」（动作及参数）、效果判断；全屏观看的步骤列表直接使用这些记录（FR-FS-7） |
| FR-LOOP-3 | 观察同时使用截图和 UI 树：截图用于理解视觉状态，UI 树用于精确读取文字（标题、时间、数量、按钮文案）和做完成验证 |
| FR-LOOP-4 | 开始前必须检查：Shizuku 在运行、目标 App 已安装、目标 App 当前不在主屏前台（6.8）；任一不满足则不开始，并说明原因 |
| FR-LOOP-5 | 同一时间只运行一个任务；任务运行期间不能下达新任务（Q-15） |
| FR-LOOP-6 | 任务终止（任何原因）后必须清理：关闭虚拟屏上的任务并释放虚拟屏（技术上必须先关任务再释放，否则会留下残留并可能破坏系统焦点，见 8.5）。**交接例外**：被交接的 App 先移到主屏，再清理其余 |

### 6.2 动作集
agent 只能使用下列动作；动作的目标都是虚拟屏。

| 动作 | 说明 | 技术实现状态 |
|---|---|---|
| 启动应用 | 在虚拟屏启动指定应用 | ✅ |
| 点击(x, y) | 触摸点击；全屏观看时以小圆点标出 | ✅ |
| 滑动 | 起点、终点、时长 | ✅ |
| 返回 | **必须**使用带 displayId 的按键事件；**禁止** `GLOBAL_ACTION_BACK`（8.3） | ✅ |
| 输入文字 | 向当前聚焦的输入框写入文字（支持中文），不使用输入法 | ✅（需先聚焦输入框） |
| 语义点击/滚动 | 通过无障碍节点执行点击、滚动，作为触摸的补充 | ✅ |
| 等待 | 等待界面稳定（页面加载、消息发送） | — |
| 询问用户 | 带选项或自由回答的问题（6.5） | — |
| 申请交接 | 到达交接边界且验证通过后触发（6.6） | — |
| 结束 | 声明完成，必须附带完成验证的证据（6.3） | — |

### 6.3 完成验证
这是「agent 说办好了时结果必须真实存在」的核心。

| 编号 | 需求 |
|---|---|
| FR-VER-1 | agent **不能**仅凭「最后一步执行成功」宣布完成。完成前必须有一次**独立的验证观察**：导航到能展示结果的界面（T1 日历列表、T2 聊天记录、T3 结算页），读取并比对 |
| FR-VER-2 | 比对必须逐项进行：每个完成标准项（标题、时间、消息内容、发送状态、商品、数量、付款按钮可见）对应一个检查结果。任一项不通过则不是完成 |
| FR-VER-3 | 精确内容（标题、时间、数量、消息文字）优先用 UI 树的文字比对，不依赖模型「看图判断」；视觉状态（发送中图标、按钮是否可见）可用截图判断 |
| FR-VER-4 | 验证不通过时：能修复的（例如时间填错）在步数和失败次数限制内修复后**重新验证**；不能修复则判定为失败，说明「期望 vs 实际」。**不允许**在验证未通过时显示「完成」 |
| FR-VER-5 | 完成时保存验证用的证据（截图和读取到的文字），在小窗和全屏观看中展示（FR-FS-9）；证据保存在本地（9.3） |
| FR-VER-6 | 结果可能因界面延迟而不稳定（如消息从「发送中」变为「已发送」）：验证前先等待稳定，等待上限见 NFR-SPEED-3 |
| FR-VER-7 | 验证用的观察必须发生在最后一个改变状态的动作**之后**，不能复用之前的截图 |

### 6.4 出错处理
| 编号 | 需求 |
|---|---|
| FR-ERR-1 | 任务最多 **30 步**（口径见 Q-10）。达到上限仍未完成：判定失败，说明「超出步数」，并说明已做到哪一步 |
| FR-ERR-2 | **同一步连续失败 3 次**：停止任务，状态为失败，在小窗说明原因。「失败」「同一步」的定义见 Q-11；建议口径：同一目标下，动作执行后界面没有出现预期变化（或验证不通过），连续 3 次 |
| FR-ERR-3 | 遇到不确定情况（多个同名联系人、含糊的时间、多个相近商品、不理解的弹窗）：**询问用户**，而不是猜测（6.5） |
| FR-ERR-4 | 网络/API 错误：对 Claude API 调用失败做有限次重试（建议 2 次，指数退避）；仍失败则任务失败，说明「无法连接 Claude」。API 重试不计入步数（Q-10） |
| FR-ERR-5 | 目标 App 崩溃或被系统杀掉：尝试重新启动一次并重新观察；仍失败按 FR-ERR-2 处理 |
| FR-ERR-6 | 失败时的现场：agent 不删除、不撤销任何已产生的内容（删除属于必须交接的操作）。失败说明里必须写明可能残留的内容（如「日历里可能已创建了一个时间不对的事项」），方便用户处理（Q-8） |
| FR-ERR-7 | 所有失败说明必须是用户能看懂的原因，不是内部错误码；同时保留完整步骤记录供查看 |

### 6.5 询问用户
| 编号 | 需求 |
|---|---|
| FR-ASK-1 | 触发条件：信息缺失或含糊（T1-R2）、多个候选无法区分（T2-R2、T3-R1）、任何可能产生不可逆后果但不属于「必须交接」的歧义 |
| FR-ASK-2 | 询问时任务进入「需要用户回答」状态，agent 暂停，直到用户回答或停止任务；**不设自动超时代替用户做决定** |
| FR-ASK-3 | 问题要具体、可回答：附带候选项（如两位「Bob」的头像/用户名/最近消息摘要），优先以**选项按钮**回答 |
| FR-ASK-4 | 需要自由文本回答（如「请告诉我具体时间」）时，**不能**在悬浮小窗里输入（小窗不获取输入焦点）；小窗上提供「回答」入口，跳转到 PhoneAgent 主界面的问答页完成输入（Q-2） |
| FR-ASK-5 | 用户回答后，回答作为任务上下文继续执行；回答要显示在步骤列表里 |
| FR-ASK-6 | 一次任务中询问次数没有硬性限制，但每次询问计为一步（Q-10） |
| FR-ASK-7 | 用户长时间不回答时，保持「需要用户回答」状态并发出通知（NFR/7.4），不自动失败（超时策略见 Q-23） |

### 6.6 交接
| 编号 | 需求 |
|---|---|
| FR-HO-1 | **交接触发**：到达该任务的交接边界，并通过边界验证后。T3：结算页商品和数量正确、付款按钮可见。T2 收件人不在通讯录：已确认该收件人不在通讯录（此时不发送）。遇到登录、密码、验证码、风控：已确认当前页面是该类页面 |
| FR-HO-2 | **验证先于交接**：未通过边界验证不得显示「需要交接」。边界验证未通过按 FR-VER-4 处理 |
| FR-HO-3 | 交接后 agent **不再对该 App 做任何操作**。任务状态为「已交接」，任务视为结束 |
| FR-HO-4 | 小窗显示「需要交接」，并**不自动**移动 App；用户点击后才把该 App 的任务从虚拟屏移到主屏前台，由用户完成剩余操作（如付款）。移动是用户主动点击触发的，不算打扰 |
| FR-HO-5 | 移动后，App 必须保持 agent 停下时的页面状态（结算页仍是结算页）；移动失败时在小窗显示明确错误，并给出备用办法（如在最近任务中打开该 App）。⚠ 任务从虚拟屏移到主屏的可行性和状态保持**未验证**，见 8.6 |
| FR-HO-6 | 用户一直不点击交接：保持「需要交接」状态并发通知；被交接的 App 一直保留在虚拟屏上，直到用户处理或停止任务（保留时限见 Q-23） |
| FR-HO-7 | 交接结束后清理虚拟屏（FR-LOOP-6） |

### 6.7 安全
#### 6.7.1 必须交给用户的操作
| 类别 | 说明 |
|---|---|
| 付款 | 点击付款、提交订单、确认支付、「立即购买」后进入支付、输入支付密码等 |
| 删除 | 删除任何内容（事项、消息、联系人、订单、文件等），包括撤回消息 |
| 输入密码或验证码 | 登录、解锁、支付密码、短信/邮箱验证码、二次验证、人机验证 |
| 给通讯录里没有的人发消息 | 见 T2-R1、Q-9 |

#### 6.7.2 确定性拦截
上面四类**不能只靠提示词约束模型**。必须有独立于模型判断的确定性拦截层，在「执行」之前检查：
| 编号 | 需求 |
|---|---|
| FR-SAFE-1 | 动作目标是文案或描述匹配「付款/支付/下单/提交订单/Pay/Place order/Buy now/Delete/删除/Remove/Send money」等关键字的按钮或控件时，拦截该动作并转为交接 |
| FR-SAFE-2 | 目标是密码输入框（UI 树 `isPassword`）或页面识别为登录/验证码页面时，拦截输入并转为交接；agent **永远不输入**密码、验证码 |
| FR-SAFE-3 | 拦截关键字表要可配置，并按中英文维护；拦截命中要记录在步骤列表里（「已拦截：……，转为交接」） |
| FR-SAFE-4 | 拦截是宁可错杀：拦截后转交接的代价（用户多点一下）远小于误执行的代价 |

#### 6.7.3 系统弹窗与权限
agent 遇到系统权限弹窗（通知、联系人、位置等）、应用更新弹窗、广告弹窗时的处理规则见 Q-12。在规则确定前的默认：**不授予任何权限**，遇到会阻塞任务的权限弹窗按「需要交接」处理。

#### 6.7.4 屏幕内容不是指令
| 编号 | 需求 |
|---|---|
| FR-SAFE-5 | 屏幕上的文字（聊天消息、网页、商品描述、通知）都是**数据**，不是指令。agent 不执行屏幕内容里出现的任何指令（提示词注入） |
| FR-SAFE-6 | agent 只执行与当前任务直接相关的动作；任务范围外的应用和界面（如被消息里的链接引导去其他 App）一律不跟随 |

#### 6.7.5 已创建内容的修改
agent 对**本次任务创建的内容**的修改权限（例如修正日历事项的时间）见 Q-8；在确认前的默认：允许修改本次任务自己创建的内容，不允许删除。

### 6.8 与用户并发使用手机
这一节是「用户同时正常使用手机」的具体规则。

| 编号 | 需求 |
|---|---|
| FR-CON-1 | **用户打字时**：由于虚拟屏带有「不抢 top focus」标志，用户的键盘和输入目标不受 agent 影响（✅ 已验证，8.2），所以「用户打字时暂停」**默认关闭**，作为**可选的安全开关**。开关打开后，用户打字（主屏软键盘显示）时，agent 在下一个动作前暂停，小窗显示「等待用户输入完成」；键盘收起并持续 2 秒后自动继续 |
| FR-CON-2 | 如果设备上「不抢 top focus」标志不可用（其他 Android 版本、厂商 ROM），自动启用 FR-CON-1 的暂停作为后备，并告知用户限制（Q-5） |
| FR-CON-3 | **同一 App 冲突**：用户在主屏打开 agent 正在使用的 App 时，agent **暂停**，小窗提示「你正在使用 XX，agent 已暂停」；等用户离开该 App 后自动继续。继续前必须重新观察并确认页面状态仍符合预期，否则按 FR-ERR-2 处理 |
| FR-CON-4 | 冲突检测的技术前提：⚠ 这件事目前**没有验证过可行的检测与恢复方式**。已知两种现象（`docs/known-issues.md` 第 1 条）：用户在主屏启动同一 App 时，请求可能被虚拟屏上的实例吸收（主屏没有任何反应），也可能把虚拟屏上的任务整个移到主屏（虚拟屏变空）。需要技术验证后才能定稿，见 Q-4 |
| FR-CON-5 | 开始任务前，如果目标 App 已经在主屏前台或最近任务里有实例，行为见 Q-4 |
| FR-CON-6 | 用户的任何主屏操作（滑动、点击、返回、Home）都不应影响 agent 的执行（除 FR-CON-3 的同一 App 冲突和 FR-CON-1 的可选暂停）。agent 的任何动作不得影响用户主屏的触摸、返回和焦点 |
| FR-CON-7 | 用户关闭 PhoneAgent 的 App 界面或切到别的 App，任务继续运行（前台服务保活，✅ 已验证） |

## 7. 界面与交互

### 7.1 任务输入
| 编号 | 需求 |
|---|---|
| FR-UI-1 | 主界面有任务输入框（支持中文），提交后开始任务。同一时间只能有一个任务（FR-LOOP-5） |
| FR-UI-2 | 提交后：若满足前置条件，创建虚拟屏、启动前台服务、显示悬浮小窗；用户可以立即切换到其他 App |
| FR-UI-3 | 主界面显示当前任务状态和最近任务记录（含失败原因、完成证据），可进入步骤详情 |
| FR-UI-4 | 设置页：API Key、「用户打字时暂停」开关、清除本地记录（9.3） |

### 7.2 悬浮小窗

#### 7.2.1 通用需求
| 编号 | 需求 |
|---|---|
| FR-FW-1 | 任务开始后，屏幕边缘出现悬浮小窗；使用「显示在其他应用上层」权限（FR-ONB-3） |
| FR-FW-2 | **可拖动，松手后吸附到屏幕边缘** |
| FR-FW-3 | **不能获取输入焦点**：不得抢走用户键盘、输入法或当前窗口焦点。⚠ 悬浮窗与键盘/焦点的交互未在技术验证中覆盖，需要验证（8.6） |
| FR-FW-4 | 所有交互都用点击完成（按钮、选项）。**小窗内没有文字输入**，因为它不能获取输入焦点（FR-ASK-4） |
| FR-FW-5 | 小窗上可直接**停止任务**（所有执行中的状态都有停止按钮） |
| FR-FW-6 | 点击小窗主体进入全屏观看模式（7.3） |
| FR-FW-7 | 小窗不遮挡键盘、系统导航；尺寸小，默认收起状态只显示图标/一行状态文字（具体形态见 Q-1） |
| FR-FW-8 | 小窗只显示在主屏（display 0）上，不显示在虚拟屏上 |
| FR-FW-9 | 状态变化时有轻量的视觉变化（颜色/图标）；「需要用户回答」「需要交接」「失败」要有更醒目的提示，并发系统通知（7.4） |

#### 7.2.2 状态表
用户指定的 6 个状态，加上必须补充的 3 个（见 Q-1 的说明）。

| 状态 | 触发 | 小窗显示 | 可用操作 |
|---|---|---|---|
| **执行中** | 任务运行 | 「第 N 步 · 当前步骤简述」（如「第 5 步 · 在日历里填写标题」） | 停止；点击进入全屏观看 |
| **等待用户输入完成** | 仅在「用户打字时暂停」生效时（FR-CON-1/2），主屏键盘显示 | 「等你输入完成后继续」 | 停止；点击进入全屏观看 |
| **需要用户回答** | agent 询问用户（6.5） | 问题文字 + 选项按钮（建议 ≤4 个）+「回答」入口（自由文本时跳转 App） | 选择选项；停止 |
| **需要交接** | 到达交接边界且验证通过（6.6） | 「已到结算页，请你付款」+「去处理」按钮 | 去处理（移动 App 到主屏）；停止（放弃交接） |
| **完成** | 完成验证全部通过 | 「已完成：结果摘要」 | 点击查看证据截图；关闭小窗 |
| **失败** | 6.4 的各种失败 | 「失败：原因」（用户看得懂的一句话） | 点击查看步骤详情；关闭小窗 |
| **暂停（用户）**⁺ | 用户在全屏观看点「暂停」 | 「已暂停」 | 继续；停止 |
| **暂停（应用冲突）**⁺ | FR-CON-3 | 「你正在使用 XX，agent 已暂停」 | 停止；用户离开该 App 后自动继续 |
| **已停止**⁺ | 用户点停止 | 「已停止」 | 关闭小窗 |

⁺ 为补充状态：用户指定的状态列表里没有，但是需求里已经出现（暂停按钮、应用冲突暂停、停止按钮）。

状态转换（概要）：
```
执行中 ⇄ 等待用户输入完成            （可选开关/后备）
执行中 ⇄ 暂停（用户）
执行中 ⇄ 暂停（应用冲突）
执行中 → 需要用户回答 → 执行中
执行中 → 需要交接 → 已交接（用户点「去处理」）
执行中 → 完成 | 失败 | 已停止          （终态）
```

#### 7.2.3 小窗生命周期
| 编号 | 需求 |
|---|---|
| FR-FW-10 | 终态（完成、失败、已停止）后，小窗保留，直到用户关闭（避免用户错过结果）；超时自动消失的策略见 Q-14 |
| FR-FW-11 | 任务结束后下一个任务开始时，小窗重新出现 |

### 7.3 全屏观看模式

#### 7.3.1 布局
```
┌──────────────────────────────┐
│ 执行中 · 步骤 7/30            │ ← 顶部细条（状态 + 步骤序号）
├──────────────────────────────┤
│                              │
│                              │
│   虚拟屏实时画面（约 85%）    │ ← 只能观看，不能点击
│   agent 的点击位置：小圆点    │
│                              │
│                              │
├──────────────────────────────┤
│        [暂停]    [停止]       │ ← 底部按钮栏（上滑展开步骤列表）
└──────────────────────────────┘
```

#### 7.3.2 需求
| 编号 | 需求 |
|---|---|
| FR-FS-1 | 点击小窗进入全屏观看；屏幕**约 85%** 显示虚拟屏实时画面（按宽高比等比缩放，不拉伸） |
| FR-FS-2 | **流畅度至少每秒 10 帧**（测量方法见 NFR-PERF-1）。⚠ 技术验证只验证了每秒 1 帧，10 帧**未验证**，见 8.6、Q-6 |
| FR-FS-3 | agent 的**点击位置用小圆点标出**：点击发生时在对应位置显示，短暂后消失。滑动的显示方式见 Q-24 |
| FR-FS-4 | **顶部细条**显示当前状态和步骤序号（「步骤 7/30」）；状态文字与小窗一致 |
| FR-FS-5 | **底部按钮栏只有：暂停、停止**。暂停后「暂停」变为「继续」。暂停语义：当前步骤执行完后停住，之后不再有新动作；虚拟屏画面保持；继续后重新观察再决策。暂停是否有时限见 Q-23 |
| FR-FS-6 | 停止：确认后终止任务（状态「已停止」），按 FR-LOOP-6 清理。停止必须在任何状态下都能立即生效，包括正在等待 Claude API 响应、正在询问用户 |
| FR-FS-7 | **上滑底部栏展开完整步骤列表**：每一步显示序号、「看到了什么」、「做了什么」、效果；包括被拦截的动作、用户的回答。列表可滚动 |
| FR-FS-8 | **实时画面只能观看，不能直接操作**：画面上的触摸不转发给虚拟屏 |
| FR-FS-9 | **任务完成时显示证据截图**（FR-VER-5）；T3 交接场景显示结算页的验证截图。⚠ 若页面是安全窗口导致画面黑屏，替代方案见 Q-22 |
| FR-FS-10 | **返回手势或下滑退出全屏**，回到小窗，agent 继续工作（不受影响） |
| FR-FS-11 | 收起为小窗（退出全屏）时，画面更新**降回低帧率**以节省电量（NFR-PERF-2）；再次进入全屏恢复高帧率 |
| FR-FS-12 | 全屏观看期间，状态变化（需要用户回答、需要交接、失败）要在全屏界面内就能处理：「需要用户回答」在此处直接回答（全屏界面是 App 自己的窗口，可以输入）；「需要交接」显示「去处理」 |
| FR-FS-13 | 全屏观看是 PhoneAgent 的界面，会占用用户主屏；进入和退出都是用户主动触发 |

### 7.4 通知
| 编号 | 需求 |
|---|---|
| FR-NOTIF-1 | 任务运行期间有常驻的前台服务通知（系统要求，Android 14 前台服务类型 `specialUse`） |
| FR-NOTIF-2 | 状态变为「需要用户回答」「需要交接」「失败」「完成」时发普通通知，点击回到对应界面（用户可能没注意角落的小窗，Q-13） |

## 8. 技术约束

来源：`docs/spike-summary.md`、`docs/known-issues.md`、`docs/ime-experiments.md`。验证环境：Android Studio 模拟器 Pixel 8、Android 14（API 34）。

### 8.1 平台与权限
| 编号 | 约束 | 状态 |
|---|---|---|
| TC-1 | 仅 Android 14（API 34）；更低版本没有「不抢 top focus」标志；厂商 ROM 未知 | ✅ 模拟器；⚠ 真机未验证 |
| TC-2 | 依赖 Shizuku：特权代码在 Shizuku UserService（shell uid）里运行；首次需要用户授权；**设备重启后 Shizuku 需要重新启动** | ✅ |
| TC-3 | 运行时权限：悬浮窗（显示在其他应用上层）、通知（Android 13+）；前台服务类型 `specialUse` | 前台服务 ✅；悬浮窗 ⚠ |
| TC-4 | 大量使用隐藏 API（反射）：`DisplayManager`、`InputEvent.setDisplayId`、`UiAutomation`、`IWindowManager`、`IActivityTaskManager`；系统版本变化会失败，需要按版本验证 | ✅ |
| TC-5 | 不引入 hiddenapibypass | — |

### 8.2 虚拟屏与键盘/输入目标隔离
| 编号 | 约束 | 状态 |
|---|---|---|
| TC-6 | 虚拟屏 1080x2400（420dpi），画面输出到 ImageReader（RGBA_8888） | ✅（真机适配 Q-19） |
| TC-7 | 创建虚拟屏必须带 `VIRTUAL_DISPLAY_FLAG_STEAL_TOP_FOCUS_DISABLED`（Android 14 隐藏常量 0x10000，需要 `OWN_FOCUS`、`TRUSTED`）。没有该标志，虚拟屏上任何 Activity 启动或获得焦点都会切走 top focused display，收起或抢走用户的键盘；有了该标志，6 步隔离测试全部通过 | ✅ |
| TC-8 | 虚拟屏的 IME 策略必须设为 `HIDE`（创建后显式设置，策略按 display uniqueId 缓存），否则虚拟屏里的 App 会在用户屏幕上弹出键盘 | ✅ |
| TC-9 | 标志是创建时的 flag，不能事后修改；不可用时的后备是「用户打字时暂停」，但后备方案不能保证键盘不被收起（`docs/known-issues.md` 第 6 条） | ✅ |

### 8.3 输入与读取
| 编号 | 约束 | 状态 |
|---|---|---|
| TC-10 | **返回键必须使用带 displayId 的 KeyEvent**；**禁止 `GLOBAL_ACTION_BACK`**：它作用于 top focused display（始终是主屏），会误关用户正在用的主屏 App | ✅ |
| TC-11 | 点击、滑动：`InputManager.injectInputEvent` + `setDisplayId`，只作用于虚拟屏，不影响主屏 | ✅ |
| TC-12 | 写入文字：`UiAutomation` + `ACTION_SET_TEXT`，支持中文，不经过输入法；目标输入框必须先获得焦点（先点击）；连接必须带 `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES` | ✅（只测过系统设置） |
| TC-13 | 界面树读取：同一个 UiAutomation 连接；首次连接后第一次读取可能还没填充，需要重试 | ✅ |
| TC-14 | 画面采集：虚拟屏静止时没有新帧；每帧必须及时关闭；采集到的是整屏截图 | ✅（1 fps） |

### 8.4 前台服务与后台
| 编号 | 约束 | 状态 |
|---|---|---|
| TC-15 | 前台服务保活：用户切到别的 App 后虚拟屏继续工作，后台注入的点击仍然生效（验证了 20 秒） | ✅（长时间、省电模式、被系统杀 ⚠） |
| TC-16 | `startForegroundService` 必须在 App 可见时调用（用户在 App 内提交任务时满足） | ✅ |

### 8.5 生命周期与清理
| 编号 | 约束 | 状态 |
|---|---|---|
| TC-17 | 释放虚拟屏之前必须先关掉虚拟屏上的所有任务，否则任务和窗口会残留在已销毁的 display 上，积累后会让系统 top focused display 卡在已销毁的 display 上、主屏所有窗口失去焦点，只能重启系统 | ✅（已修复并验证） |
| TC-18 | 重装/升级 App 后，旧版 UserService 可能残留；需要版本号管理（`docs/known-issues.md` 第 3 条） | ⚠ 正式版需要处理 |

| 编号 | 能力 | 对应需求 |
|---|---|---|

| UV-3 | **同一 App 冲突的检测与恢复**：检测用户在主屏打开了 agent 在用的 App；任务被移到主屏后，如何移回虚拟屏继续 | FR-CON-3/4/5 |
| UV-4 | **悬浮窗**（`TYPE_APPLICATION_OVERLAY` + 不可聚焦）与用户键盘、焦点、top focused display 的交互；拖动吸附 | FR-FW-3 |

| UV-8 | 标志在真机、厂商 ROM、其他 Android 版本上是否有效 | TC-1、TC-7 |
| UV-9 | 动作之间的耗时（点击后页面稳定需要多久）、Claude API 每步耗时、端到端任务耗时 | NFR-SPEED |

## 9. 非功能需求

### 9.1 速度
下列指标为**建议值**（待产品确认，Q-6、Q-20），UV-9 验证后调整。

| 编号 | 指标 | 建议值 |
|---|---|---|
| NFR-SPEED-1 | 提交任务到开始第一步（虚拟屏创建、小窗出现） | ≤ 3 秒 |
| NFR-SPEED-2 | 单步耗时（观察 → 决策 → 执行 → 确认） | 中位数 ≤ 8 秒（主要是 Claude 响应） |
| NFR-SPEED-3 | 完成验证中等待状态稳定的上限（如消息从「发送中」变成「已发送」） | ≤ 20 秒 |
| NFR-SPEED-4 | 端到端任务时长（含询问用户前的部分） | T1 ≤ 2 分钟；T2 ≤ 90 秒；T3 ≤ 4 分钟 |
| NFR-SPEED-5 | 停止操作的响应时间 | ≤ 1 秒生效，≤ 3 秒清理完成 |
| NFR-SPEED-6 | 点击小窗进入全屏观看 | ≤ 500 毫秒出现画面 |

### 9.2 性能与电量
| 编号 | 指标 | 说明 |
|---|---|---|
| NFR-PERF-1 | 全屏观看帧率 ≥ 10 fps | 测量方法：连续滚动页面 10 秒，统计界面实际收到并显示的帧数，平均 ≥10；需在 UV-1 验证后确认目标是否现实 |
| NFR-PERF-2 | 非全屏时画面采集降到低帧率（建议 ≤ 1～2 fps，仅供 agent 观察） | 节省电量；FR-FS-11 |
| NFR-PERF-3 | 运行 5 分钟任务的额外耗电、发热、内存不应让手机明显卡顿 | 具体指标待 UV-9 |
| NFR-PERF-4 | agent 的注入与采集不应影响用户主屏的触摸响应和输入延迟 | 以 ime_test、back_test 回归为底线 |

### 9.3 隐私
agent 会看到用户第三方 App 里的内容（聊天、日程、购物信息）。v1 没有后端，数据流是「手机 → Claude API」，以及本地存储。

| 编号 | 需求 |
|---|---|
| NFR-PRI-1 | 首次使用前明确告知并取得同意：虚拟屏截图和界面文字会发送给 Claude API（FR-ONB-6）；用户可随时在设置里看到该说明 |
| NFR-PRI-2 | **数据最小化**：只在任务运行期间采集虚拟屏；截图缩小到模型所需分辨率；不采集主屏内容（用户自己屏幕上的内容永远不上传） |
| NFR-PRI-3 | 密码输入框（`isPassword`）的内容不得发送；包含密码框的画面区域在发送前遮盖；`FLAG_SECURE` 窗口不上传（也无法截取） |
| NFR-PRI-4 | 不向除 Claude API 以外的任何服务发送截图、界面文字、任务内容；**没有分析/遥测**（v1） |
| NFR-PRI-5 | 本地保存任务记录（指令、步骤列表、证据截图），保存在应用私有存储，其他应用不可读；默认保留期限和用户清除方式见 Q-17 |
| NFR-PRI-6 | 通知、日志、崩溃信息中不含第三方 App 的内容（FR-NOTIF-3）；日志中不记录截图内容和 API Key |
| NFR-PRI-7 | 应用不允许系统备份任务记录和密钥（当前代码 `allowBackup=true`，**发布前必须改为 false** 或排除相关数据） |

### 9.4 API Key 安全
| 编号 | 需求 |
|---|---|
| NFR-KEY-1 | v1 由用户自行提供 API Key，保存在 Android Keystore 保护的加密存储中，不明文落盘 |
| NFR-KEY-2 | Key 不出现在日志、截图、通知、崩溃报告、调试广播和备份中；输入时遮蔽显示 |
| NFR-KEY-3 | Key 只用于调用 Claude API，不发送到其他任何地址 |
| NFR-KEY-4 | 用户可随时删除/更换 Key；删除后立即停止正在运行的任务 |
| NFR-KEY-5 | 明确告知用户：Key 保存在本机，root 过的设备上可能被提取（BYO Key 的固有风险）；设置每个任务的费用/调用上限防止异常消耗（Q-16） |
| NFR-KEY-6 | 调试用的 adb 广播入口（`CmdReceiver`）只存在于 debug 构建，发布构建中不得出现（已通过 `src/debug` 源码集保证，发布前再核对一次） |
| NFR-KEY-7 | Shizuku 授权给 PhoneAgent 的特权通道（shell 权限）不得暴露给其他应用；PhoneAgent 自身不提供让第三方触发特权操作的入口 |

### 9.5 可靠性
| 编号 | 需求 |
|---|---|
| NFR-REL-1 | 任何终止原因（完成、失败、停止、App 被关闭、崩溃后重启）之后，虚拟屏都被清理，不留下残留任务/窗口，不让主屏失去焦点（TC-17） |
| NFR-REL-2 | App 或 UserService 异常退出后，重新打开 App 时检测并清理遗留的虚拟屏；任务不自动恢复，状态显示为失败/已停止 |
| NFR-REL-3 | 三类任务各有可重复的验收脚本（扩展 `scripts/`），包含完成验证的断言；每次改动 `priv/`、agent 循环后跑 `scripts/regress.sh` 和任务验收 |
| NFR-REL-4 | 失败不能静默：每个失败都有用户可读的原因（FR-ERR-7） |

### 9.6 兼容与本地化
| 编号 | 需求 |
|---|---|
| NFR-L10N-1 | PhoneAgent 界面语言：简体中文（v1） |
| NFR-L10N-2 | 目标 App 可能是中文或英文界面；agent 必须两种都能理解；拦截关键字表中英文并存（FR-SAFE-3） |
| NFR-L10N-3 | 任务指令支持中文、英文 |

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 「不抢 top focus」标志在真机/厂商 ROM 上无效 | 用户键盘会被收起或抢走，产品核心承诺不成立 | 优先用真机验证（UV-8）；后备是「用户打字时暂停」，但不能完全保证键盘不被收起（TC-9）；v1 发布门槛包括真机验证 |
| 第三方 App 在虚拟屏上运行异常、`ACTION_SET_TEXT` 不生效 | 任务不可用 | UV-5 先验证三个目标 App |
| 付款/结算页是安全窗口（黑屏） | T3 的画面验证和证据截图失效 | 用 UI 树文字做验证；证据降级（Q-22）；UV-6 |
| 同一 App 冲突没有可行的检测/恢复 | T2（用户常在 Telegram 聊天）体验差 | UV-3；开始前检查并提示（Q-4） |
| 10 fps 达不到 | 全屏观看体验差 | UV-1；备选方案：降到 5 fps；或把虚拟屏输出切到 SurfaceView |
| Claude 误操作：点错、重复提交、被屏幕内容注入 | 产生不可逆后果 | 确定性拦截（6.7.2）、验证先于完成、幂等检查（T1-R5、T2-R4）、屏幕内容不是指令（FR-SAFE-5） |
| Shizuku 门槛高，重启后要重新启动 | 用户流失、频繁失败 | 引导和状态检测（FR-ONB-2）；接受 v1 面向技术用户 |
| 分发渠道限制：依赖隐藏 API 和 Shizuku，可能不符合应用商店政策 | 只能侧载 | v1 不承诺上架（Q-18） |
| 用户 API 费用失控 | 费用 | 每任务上限（Q-16） |
| 步数上限 30 不够完成 T3 | 任务失败率高 | UV-9 实测每类任务的步数，必要时调整上限（Q-10） |

### 11.2 需求之间的矛盾/张力
1. **「小窗显示状态」vs「收起为小窗时画面降回低帧率」**：见 Q-1。
2. **「小窗不能获取输入焦点」vs「需要用户回答」**：小窗里不能打字，见 Q-2。
3. **「等待用户输入完成」状态 vs 「用户打字时暂停」可能改为可选**：状态表里有，默认却关闭，见 Q-5。
4. **「用户在主屏打开 agent 正在使用的 App 时，agent 暂停，等用户离开后继续」vs 技术验证**：验证里 App 要么被吸收要么被抢走，没有「暂停后继续」的路径，见 Q-4。
5. **T2「给联系人发消息」vs「给通讯录里没有的人发消息必须交接」**：「联系人」的定义未统一，且「交接」对发消息意味着什么（App 移到主屏，消息未发送）没有定义，见 Q-9。
6. **「完成时显示证据截图」vs 付款页安全窗口**：T3 的证据可能为空，见 Q-22。
7. **「最多 30 步」vs T3 的复杂度**：选品、规格、加购、进结算页，30 步可能不够，见 Q-10。
8. **「流畅度至少每秒 10 帧」vs 技术验证的 1 fps**：见 Q-6。
9. **「删除必须交给用户」vs 失败后的清理**：agent 创建错了东西不能自己删，见 Q-8。
10. **「返回手势或下滑退出全屏」vs 「上滑底部栏展开步骤列表」**：手势方向相反但在同一个界面，需要避免冲突（建议下滑只在顶部细条/画面区域触发）。

## 附录 A：术语
| 术语 | 含义 |
|---|---|
| 虚拟屏 | `VirtualDisplay`，用户看不见的屏幕，agent 在上面操作第三方 App |
| 主屏 | 用户手机真实屏幕（display 0） |
| top focused display | 系统当前接收按键和决定键盘归属的屏幕；虚拟屏抢走它会收起用户键盘 |
| UI 树 | 通过无障碍接口读到的界面节点结构（文字、位置、是否可点击） |
| 交接 | agent 停在边界处，由用户接手剩余操作 |
| 完成验证 | 完成前独立读取结果并逐项比对 |
| 证据 | 完成验证时保存的截图和读取到的文字 |
